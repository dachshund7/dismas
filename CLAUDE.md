# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Upstream policy on AI contributions

This repository is a fork. The upstream project (gitlab.gnome.org/World/amberol) **does not accept contributions generated by LLMs**, and its contribution guide names Claude explicitly. This covers code, docs, issues and artwork. This fork's own CONTRIBUTING.md welcomes AI-assisted work, but none of it goes upstream. Don't prepare merge requests, issues or other upstream submissions from AI-generated work.

Flathub has a similar policy (the Generative AI policy in docs.flathub.org's requirements): a Flathub manifest must not contain AI-generated or AI-assisted content, AI tools must not open a submission or write its description, commits or replies, and AI-generated code in the app must be disclosed. Don't write a Flathub manifest or prepare a Flathub submission. The manifests in this repository are for building the app outside Flathub.

## Build and run

Dismas is a GTK4/libadwaita music player written in Rust, forked from Amberol. The app ID is `io.github.dachshund7.Dismas`. Build it with Meson, which runs Cargo itself.

```sh
meson setup _build                     # add -Dprofile=development for a debug build with the .Devel app ID
meson compile -C _build                # or: ninja -C _build
meson devenv -C _build ./src/dismas    # run uninstalled
```

- **Generated `config.rs`:** `meson setup` writes `src/config.rs` from `src/config.rs.in` and copies it into the source tree, where it's gitignored. Cargo, rustfmt and clippy all need it, so a plain `cargo build` fails until Meson has run.
- **Profiles:** the default profile builds `--release`, into `_build/src/`. `Cargo.toml` has no release profile of its own, so a local release build rebuilds in about 25 s and keeps the symbols that perf needs; the shipped builds (the tarball and the Flatpak) set LTO and one codegen unit themselves. Development builds log Dismas's debug messages, release builds its messages from info up. `RUST_LOG` (e.g. `dismas=debug`) replaces that default rather than adding to it.
- **Stale resources:** the gresource bundle doesn't track the compiled `.ui` files, so after a `.blp` file is edited, the first `ninja` run can leave the old UI in `_build/src/dismas.gresource`. Run `ninja` a second time.
- **Dependencies:** at run time, gtk4 ≥ 4.19.5, libadwaita ≥ 1.8, GStreamer ≥ 1.20 (incl. plugins-bad), and the glycin loaders (`glycin-loaders`, plus `bwrap` outside Flatpak) to decode cover art. At build time, `blueprint-compiler`, `msgfmt` (gettext), and the development files of SQLite ≥ 3.45.3 (rusqlite links the system's), libseccomp (for glycin and the GStreamer reader's sandbox) and fontconfig (for glycin).
- **Installed data** (`data_paths` and `schema_dirs` in `main.rs`): the resource bundle and the translations are looked for next to the binary first (`../share/dismas`, `../share/locale`), then at the paths Meson built in, so a build unpacked anywhere runs.
- **Flatpak:** `io.github.dachshund7.Dismas.json` builds the regular app, which releases ship, and `io.github.dachshund7.Dismas.Devel.json` the Devel one, which CI builds. They differ only in the app ID, the profile and each profile's variables; keep the rest the same. Both build on the GNOME 51 runtime from the folder they're in, and let Cargo download the crates (`--share=network`). They read the music through both `xdg-music:ro` and `~/Music:ro`, as `xdg-music` shares nothing where no `user-dirs.dirs` sets `XDG_MUSIC_DIR`. A file that came through the document portal has a path under `/run/user/<uid>/doc/` in the sandbox; its path outside (`utils::ATTRIBUTE_HOST_PATH`) only names it and can't be opened.
- **Prebuilt tarball** (`build-aux/make-tarball.sh`): a release build laid out as `dismas-<version>-<arch>/`, which runs from wherever it's unpacked. Its schema is compiled in `share/dismas/schemas`, not `share/glib-2.0/schemas`, where a compiled schema unpacked into `~/.local` would replace other apps' ones. The script fails if the binary needs a newer glibc than `MAX_GLIBC`, builds in `_build-tarball`, and puts `src/config.rs` back afterwards. `build-aux/install.sh` adds the app to the user's menu, and only replaces or removes the links and files it made.

## Checks

```sh
cargo fmt --all -- --check                  # needs src/config.rs; a blank line is enough (CI writes one)
cargo clippy --all-targets -- -D warnings   # keep it free of warnings
cargo test                                  # unit tests are in #[cfg(test)] modules next to the code
cargo test <name>                           # a single test
build-aux/checks.sh                         # fmt, typos (configured in .typos.toml), POTFILES.in, resource order
reuse lint                                  # REUSE/SPDX licensing; needs reuse ≥ 4, older ones ignore REUSE.toml
cargo deny check advisories                 # the dependencies against the RustSec advisories
```

Every source file needs SPDX headers (`SPDX-FileCopyrightText` / `SPDX-License-Identifier`). REUSE.toml covers files that can't carry headers.

Some ignored tests are tools for checking changes on real data: `print_palettes` (cover colors of a music folder), `print_work_splits` (recordings split on the albums of `DISMAS_LIBRARY_DB`), `time_scan`, `time_library_searches` and `time_performers` (opening the Performers picker). Tests never read the user's music or `plays.db` (the library's tests take their play stats from `TEST_SEARCH_STATS`).

GitHub Actions (`.github/workflows/`):

- `ci.yml`, on pushes to main and on pull requests: `lint` runs `checks.sh` and `reuse` on Ubuntu. `build` builds with Meson and runs clippy, the tests and the data file validation in `fedora:latest`, as Ubuntu's GTK and libadwaita are too old, and fails if they changed Cargo.lock (they run Cargo without `--locked`). `flatpak` builds the Devel manifest in the `flatpak-github-actions:gnome-51` image. To try `build` locally, run its commands in `podman run fedora:latest`.
- `advisories.yml` runs `cargo deny check advisories` (`deny.toml`) when Cargo.lock, `deny.toml` or the workflow change, and on main every day.
- `release.yml`, on a version tag (`20*`), builds the regular Flatpak and the tarball and puts them in a draft release whose notes are the version's section of CHANGES.md. It's checked and published by hand (RELEASING.md).
- When editing the workflows, keep their hardening: actions are pinned to commits, with the release in a comment, and updated by hand in all the files together at the start of each cycle (RELEASING.md), with no Dependabot. Only release.yml's `draft` job can write to the repository, and it runs none of the repository's code; the build jobs get a read-only token, checkouts don't keep it (`persist-credentials: false`), and release.yml's Flatpak build doesn't use the Actions cache, which runs on main of code that isn't pinned can write to.

## Architecture

The comments next to the code explain why it works as it does. This section is a map, and a list of the rules that hold across files.

### Playback

- **Message passing** (the header comment of `src/audio.rs`): GStreamer and the controllers fire from other threads, so nothing touches the UI's state directly. `AudioPlayer` (`audio/player.rs`), owned by `Application`, is the hub. `GstBackend` (`audio/gst_backend.rs`) wraps GstPlay and reports changes over a channel. Controllers (the `Controller` trait: MPRIS, suspend inhibition, the tray) are pushed state changes, and they and the UI send `PlaybackAction`s back. `PlayerState` (`audio/state.rs`) is the GObject the UI binds to, and is only changed on the main context.
- **Gapless playback** goes around GstPlay, whose `set_uri` stops the pipeline: the player publishes the next track (`update_next_track`), the backend hands it to playbin on about-to-finish, and sends `TrackAdvanced` on stream-start. Stopping or starting GstPlay while a track is handed over can hang it, so `gst_backend.rs` skips the hand-over in the cases where that can happen.
- **A track that hasn't played is never paused in GStreamer** (`GstBackend::pause`, `resume_at`): with PulseAudio, a pipeline prerolled to PAUSED and played later keeps its position stuck.
- **Only local files:** GStreamer is started with `audio::init_gstreamer`, never `gst::init`. It takes away the rank of the demuxers that fetch streams from the network, and the backend drops `redirect` messages, so that a file in the music folders can't make Dismas reach a server.
- **The queue** (`audio/queue.rs`) is a `GListModel` of `Track`s. Shuffling (`audio/shuffle.rs`, weighted by the play stats) and sorting (`audio/sort.rs`) reorder it for real and save it, moving the movements of a work that are next to each other as one (`work_sections::continues_work`).
- **The play stats** (`play_stats.rs`): `ListenTracker` measures each listen from the positions; the listens feed the smart playlists, the shuffle and Play a Random ….

### Reading music files

Files in the music folders can be crafted, and the library scans them at every start, so a file that crashes or hangs a read would do so at every start. Every read keeps to these rules:

- Dismas never writes to music files. `clippy.toml` bans lofty's write API, and CI fails on it; tests write tags only through `utils::write_test_id3v2`.
- Tags are only read through `read_file_tags` (`audio/track/tags.rs`). Where lofty misreads or leaves out an item, `audio/track/lofty_gaps.rs` fills it in, each gap with a canary test. lofty comes from a fork with one commit on its release, a limit on how deep ID3v2 chapter frames nest (`[patch.crates-io]` in `Cargo.toml`: the `chapter-depth-limit` branch of github.com/dachshund7/lofty-rs). **Upgrading lofty:** rebase that commit onto the new release, push it and pin its hash, or drop the patch once lofty has a limit of its own; then run `cargo test lofty_gaps` and follow the messages of the tests that fail.
- Files that lofty can't read are read with GStreamer's Discoverer (`audio/track/discovered.rs`), in a child process: Dismas started again as `/proc/self/exe --discover-file`, which `main` handles before it makes the application. A crash or a hang there only leaves that file unread.
- **The child's sandbox** (`sandbox.rs`): before GStreamer starts, the child confines itself with Landlock and a seccomp allowlist, so that a file that exploits a plugin can only read the system's files and its own, and write its report. Everything is applied before `gst::init`, which starts the threads. The parent starts the child with only the environment variables that `sandbox::child_environment` passes on, and ends it if it runs past its time. seccomp is required (a child without it exits with `EXIT_NO_SANDBOX` and leaves its file unread); Landlock is best effort, as older kernels lack it. A call that isn't allowed fails with ENOSYS, and a file that isn't granted with EACCES: when GStreamer or glibc needs a new one, grant it in `sandbox.rs`, after finding it by tracing the child (`dismas --discover-file covers <file>`; gdb's `catch syscall` works where strace isn't installed). `the_sandbox_holds` tries the sandbox in a process of its own.
- Each read of an untrusted file goes through `utils::guarded`, which catches a panic, and opens the file with `utils::open_regular_file`, never `File::open`, as opening a named pipe waits for a writer.
- Everything read from a file has a limit on its size, count or time (the `MAX_*` constants, `COVER_SEARCH_TIME`, `sane_duration`), and no work grows faster than what the file holds. A new reader of file data needs one too.
- Cover art is decoded with glycin, in sandboxed loader processes (`cover_image.rs`), never on the main thread. `CoverCache` (`audio/cover_cache.rs`) shares one decoded cover between an album's tracks.
- `load_tracks` (`audio/track/loader.rs`) reads in worker threads (`utils::in_threads`) and sends `TrackData`; the main thread wraps it in `Track` GObjects, which aren't `Send`. A playlist's file that gives no track becomes a placeholder (`TrackData::missing`), which keeps its place.
- **CUE sheets** (`cue_sheet.rs`): a track of a sheet has a path under the sheet (`Album.cue/track03`, or `Album.flac/track03` for a sheet in the tags), so the queue, playlists, resume points and the library keep it like a file's path. `Track::audio_file()` is the file that plays, and `Track::segment()` the part of it; positions and seeks are relative to the track.

### Tags, works and credits

- `audio/track.rs` has `TrackData` and the `Track` GObject; `audio/track/` has the credits (`credits.rs`), the search text, the Work Hierarchy tag (`work_hierarchy.rs`), titles from file names and the loader.
- **Works:** a track is a movement when its tags name a work and a movement. Dismas prefers the JSON tag of Picard's Work Hierarchy plugin to the plain tags; the plugin makes the decisions, and Dismas only shows them. The library tells works apart by the MusicBrainz id the hierarchy picks, or else MUSICBRAINZ_WORKID for a whole work, or else the name and the composers. An arrangement is listed under the work it arranges (`library::listed_under`).
- **Years** are when a track was recorded (RECORDINGDATE, which the plugin writes), or else ORIGINALDATE, or else DATE.

### Library and search

- **The library** (`library/`, SQLite through rusqlite) is a cache, with a row per track. A schema bump drops the tracks, which the scan reads again (`keep_added_times` keeps when they were added). The scan (`library/scan.rs`) compares each file's time and size, skips hidden folders and recycle bins, reads what a symbolic link leads to once, and keeps the tracks of a folder that's missing or couldn't be read whole, hidden rather than dropped. `library/watch.rs` watches the local folders and scans again after changes. Music folders are the `music-folders` setting, an `a(ss)` of each folder's URI and its host path for one that came through the portal; empty means the XDG Music folder.
- **`plays.db`** (`play_stats.rs`) holds what can't be read again from anywhere: the listens, their totals, and the favorite tracks, albums, works and recordings. Its tables are never dropped; a new version only changes them in place, and a version newer than the build is left alone. The window reads and writes favorites on the main thread, so that two clicks are written in order.
- **The search syntax** (`search_query.rs`, `search_query/`) is one grammar for the search boxes and, later, the rules of smart playlists (`Mode::Rule`, which is strict, so that a saved rule keeps its meaning). The queue's search (`search.rs`) and the album grid's use the same evaluator; the library runs it in SQL as `dismas_match(...)`, which `open_at()` adds to every connection. `Query::to_text` prints the canonical form, which must parse back to the same query (`print_then_parse_is_identity`).
- **Search fields** (`audio/track/fields.rs`): each track's fields are packed into one `code\tvalue\n` string, kept in the library's `fields` column, so changing a code needs a schema bump. The queue and the library must encode the same fields (`the_queue_and_the_library_encode_the_same_fields`). `normalize_key_text` must not change, as `plays.db` keeps the favorite works by keys made with it.

### UI

- **Composite templates:** each widget is a Rust subclass (`src/*.rs`) bound to a Blueprint template in `src/gtk/*.blp`. Meson compiles them to `.ui` and bundles them with the CSS and icons through `src/dismas.gresource.xml`; templates load from `/io/github/dachshund7/Dismas/<name>.ui`. **Adding a widget:** update the `.blp` list in `src/gtk/meson.build`, the gresource XML and `po/POTFILES.in` together.
- **`Window` is the coordinator:** `window.rs` holds its template, properties and `win.*` actions, and its methods are split by area into `window/*.rs`. The album pages are `LibraryView` (`library_view.rs`, `library_view/`), one grid for the Albums page, whole albums or, with the Tracks toggle, only the tracks the search matches, plus the Works page (`library_view/works.rs`).
- **Where features live:** lyrics in `lyrics.rs`, `lyrics_view.rs` and `window/pane.rs` (the pane's pages and `PaneHistory`); zoom in `zoom.rs` and `window/zoom.rs`; Zen Mode in `window/zen.rs` and `player_box.rs`; fullscreen in `window/fullscreen.rs`; Match Cover Art in `window/now_playing.rs` and `cover_image.rs`; booklets in `booklets.rs`; the composer and performer pickers in `library_view/pickers.rs`; smart playlists and Play a Random … in `window/smart_playlists.rs`; the sleep timer in `audio/sleep_timer.rs` and `window/sleep_timer.rs`; resume points in `resume_point.rs`; Find Missing Tracks in `window/find_missing.rs`; the copies kept in the export folder in `kept_copies.rs` and `window/kept_copies.rs`; the tray in `audio/tray_controller.rs` and `x11_stacking.rs`; migrating from Amberol in `migrate.rs`.
- **Playlists** (`playlists.rs`) are M3U8 files in `~/.local/share/dismas/` (`queue.m3u8`, `playlists/`, and `unshuffled/` for the order before shuffling). One playlist is selected at a time, loaded into the player's single `Queue`. Tracks are read into the queue one load at a time, in the order asked (`Window::after_loads`, and `after_startup` for files given at startup); anything that adds or replaces tracks goes through it, or the tracks land in another playlist's file. Names go through `check_name` and `path_in`, as they also come from the settings and over D-Bus. Exports (`playlists::export_text`) are written for other players: paths relative to the playlist within its music folder, compared outside the sandbox (`ExportPaths`), `#EXTINF` lines, and tracks of CUE sheets as Strawberry writes them; Dismas's own files keep the paths under the sheet, which the library, the resume points and `plays.db` know tracks by. Dismas is the only writer of the copies it keeps in the export folder: they're written from its own files by one thread, and never over a copy that another program changed, unless the user says to.
- **Actions over D-Bus:** GtkApplication exports the window's actions on the session bus, so an action that opens files or deletes data (`win.open-booklet`, `win.clear-play-history`) is installed on the class instead, where other programs can't reach it.
- **Settings** are GSettings (`data/io.github.dachshund7.Dismas.gschema.xml`), in the Preferences dialog (`preferences_dialog.rs`); the main menu only has actions. `playlist-visible` is only stored when the user shows or hides the pane (`user-playlist-visible`), not when it opens by itself.
- **File drops** all go to one drop target, on the window's drag overlay (`drag_overlay.rs`, `file_drop_at`): on X11, a second target that took a drag without getting the drop would turn the next one down.
- **Fitting the window:** sizes come from measuring the content, as they depend on the font DPI (`PlayerBox`, `Window::size_allocate`), and every page fits in 360 pixels.
- **Keyboard shortcuts:** GTK runs the application's accels before the focused widget sees the key, so a key that a focused widget can use too (Space, Home, End, Ctrl+A, Ctrl+C, Ctrl+Z…) isn't an accel but a shortcut in the window's capture or bubble phase, which leaves it to the text entries and sliders that use it (`setup_key_shortcuts` and the functions next to it in `window.rs`). Ctrl+F and typing go to the search of where the focus is (`window/find.rs`).
- **GTK pitfalls** that the helpers in `utils/ui.rs` work around:
  - Tooltips that change are made in `query-tooltip` (`set_row_tooltip`), never set as rows are bound: on X11 setting one grabs the X server, and lists bind many rows a frame while they scroll.
  - A list with headers is scrolled to its top through `scroll_to_top_when_laid_out`, as GTK ignores or undoes a scroll made in the frame its items change.
  - When a menu's action takes away the row it was opened on, GTK keeps a chain of focus children that leads nowhere, and the keys skip the list; `forget_focus_above` and `forget_focus_below` drop it.
  - Idle callbacks don't run while a list scrolls, so work that must keep up with scrolling (reading the grid's covers) runs in the map handler.
  - A flow box's arrow keys move from its cursor, which `grab_focus()` on a child doesn't move, so a child is focused with `focus_flow_box_child`.
- **Screen readers:** GTK names an icon-only button by its tooltip, so only widgets without one need an `accessibility` label. In selection mode, whether a row is selected is set on the list's item, not the row, and only while the row is mapped, as a list binds a row before it takes its item. AT-SPI names can be read with the system Python's `Atspi` bindings, in a headless session with `at-spi-bus-launcher`.
- **Touch:** menus also open with a touch-only `GestureLongPress`; a gesture inside a scrolled list acts when it's let go of, so that the list still scrolls.

### Translations

- UI strings use gettext helpers from `src/i18n.rs` in Rust, and `_()` / `C_()` in Blueprint.
- `po/*.po` files came from upstream's translators (GNOME's Damned Lies). Don't rewrite them wholesale; when a source string changes, keep the edit to the affected entries. Translations that couldn't follow the rename from Amberol are marked fuzzy. New translatable files go in `po/POTFILES.in`.

## Conventions

- Commit messages: a one-sentence summary line of at most 72 chars, capitalized, with no trailing period. Then a blank line and a prose body explaining *why*. Use `Closes #N` / `Fixes #N` for issues.
- Items are `pub(crate)`, never `pub`: the subclasses implement glib's public traits, so rustc counted the `pub` methods of most types as the crate's API and never reported one that nothing uses. Code that only tests use is `#[cfg(test)]`, and code kept for a feature to come is `#[allow(dead_code, reason = …)]`.
- Dismas never writes to music files (see Reading music files).
- The UI calls audio files "tracks" (not "songs"). Keep the freedesktop icon name `media-playlist-repeat-song-symbolic` as is.
- Every UI change works for keyboard, touch and screen-reader users. Each action has a keyboard path: menus open with the Menu key (`utils::setup_menu_key`), drags have a key or a menu item, and a key that a focused widget uses isn't an accel. A right click or hover has a touch equivalent, and custom widgets and buttons that repeat on each row get accessible names. When checking a change, read the names that AT-SPI gets too. Touch can't be tried on a device here, so touch code keeps to what GTK's gesture rules document.
- Keep this file to a map and the rules that hold across files. Explain how a feature works, and why, in comments next to its code.
