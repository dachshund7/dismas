# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Upstream policy on AI contributions

This repository is a fork. The upstream project (gitlab.gnome.org/World/amberol) **does not accept contributions generated by LLMs**, and its contribution guide names Claude explicitly. This covers code, docs, issues and artwork. This fork's own CONTRIBUTING.md welcomes AI-assisted work, but none of it goes upstream. Don't prepare merge requests, issues or other upstream submissions from AI-generated work.

## Build and run

Dismas is a GTK4/libadwaita music player written in Rust, forked from Amberol. The app ID is `io.github.dachshund7.Dismas`. Build it with Meson, which runs Cargo itself. A plain `cargo build` fails until Meson has generated `src/config.rs`.

```sh
meson setup _build                     # add -Dprofile=development for a debug build with the .Devel app ID
meson compile -C _build                # or: ninja -C _build
meson devenv -C _build ./src/dismas    # run uninstalled
```

- **Generated `config.rs`:** `meson setup` writes `src/config.rs` from `src/config.rs.in` and copies it into the source tree. The file is gitignored. Cargo, rustfmt and clippy all need it to exist.
- **Profiles:** the default profile builds `--release`. Cargo's target dir is `_build/src/`.
- **Runtime dependencies:** gtk4 ≥ 4.19.5, libadwaita ≥ 1.8, GStreamer ≥ 1.20 (incl. plugins-bad), and the glycin loaders (`glycin-loaders`, plus `bwrap` outside Flatpak) to decode cover art. At build time: `blueprint-compiler`, `msgfmt` (gettext), the SQLite development files for the library database (rusqlite links against the system SQLite), and the libseccomp and fontconfig development files, which glycin links against.
- **Flatpak:** the manifest is `io.github.dachshund7.Dismas.json`. It builds the Devel profile, on the GNOME 51 runtime, from the folder it's in (a `dir` source, skipping the build folders), and lets Cargo download the crates during the build (`--share=network`), which Flathub wouldn't allow. Inside the sandbox, the data is under `~/.var/app/io.github.dachshund7.Dismas.Devel/`, so there's nothing to migrate from Amberol.

## Checks

GitHub Actions (`.github/workflows/ci.yml`) runs these on pushes to main and on pull requests. The `lint` job runs `checks.sh` and `reuse` on Ubuntu. The `build` job builds the app with Meson and runs clippy, the tests and the data file validation in a `fedora:latest` container, because Ubuntu's GTK and libadwaita are too old. The `flatpak` job builds the manifest in the `ghcr.io/flathub-infra/flatpak-github-actions:gnome-51` image and uploads `dismas-devel.flatpak` as an artifact. To try the `build` job locally, run its commands in `podman run fedora:latest`; the `flatpak` job, with `flatpak-builder` in that image (`podman run --privileged`).

```sh
cargo fmt --all -- --check                  # needs src/config.rs; a blank line is enough (CI writes one)
cargo clippy --all-targets -- -D warnings   # keep it free of warnings
cargo test                                  # unit tests are in #[cfg(test)] modules next to the code
cargo test <name>                           # a single test
build-aux/checks.sh                         # fmt, typos (configured in .typos.toml), POTFILES.in, resource order
reuse lint                                  # REUSE/SPDX licensing; needs reuse ≥ 4, older ones ignore REUSE.toml
```

Every source file needs SPDX headers (`SPDX-FileCopyrightText` / `SPDX-License-Identifier`). REUSE.toml covers files that can't carry headers.

## Architecture

### Audio: message passing between threads

`src/audio.rs` has a header comment explaining the design. GStreamer and the controllers can fire from other threads, so nothing touches the UI state directly. Everything goes through async channels:

- `AudioPlayer` (`audio/player.rs`) is the hub. `Application` (`application.rs`) owns it and gives it a sender for `ApplicationAction`s.
- `GstBackend` wraps GstPlay and reports changes over a channel.
- Gapless playback goes around GstPlay, whose `set_uri` stops the pipeline. The player publishes the next track (`update_next_track`), as a `TrackSource`: the track's URI, which tells tracks apart, and the audio file's, which plays. On playbin's about-to-finish, the backend hands it to playbin, one track at a time. On stream-start it sends `TrackAdvanced`, and the player follows without touching the pipeline. Without a hand-over, EOS leads to `PlayNext` as before. GstPlay changes the pipeline's state and loads tracks on its own thread, and stopping or starting it while a track is handed over can hang GstPlay, so the hand-over is skipped while the playbin's state lock is held, while a load is pending (counted until each `uri-loaded`), and within 500 ms of the last load (rapid skipping). A generation number lets the player ignore switches from before it loaded a track. `stop` loads the track again, since uridecodebin3 would keep a track that was handed over. rgvolume only resets on EOS, so the ReplayGain bin sends it an EOS of its own at each stream-start and drops it after rgvolume.
- Controllers implement the `Controller` trait (`audio/controller.rs`) and are pushed state changes by the player:
  - `MprisController`: media keys and desktop integration.
  - `InhibitController`: prevents suspend during playback.
  - `TrayController` (Linux/FreeBSD): a StatusNotifierItem through ksni, which runs on a thread of its own, so the tray sends `ApplicationAction`s (`ToggleWindow`, `Present`, `Quit`) and `PlaybackAction`s. It's shown while `background-play` is on, and waits for a tray host if there's none yet. Its icon is a simple blue one of its own (`<app ID>-tray`, installed renamed from one source for both profiles), since the app icon is too detailed at tray sizes. It isn't symbolic, as trays would recolor it. The app ID prefix lets Flatpak export it to the host. Clicking it closes the window if it has the focus, or if it's on screen and nothing covers it (with focus following the pointer, moving to the tray focuses other windows), and presents it otherwise (`closes_on_click` in `application.rs`). GTK knows neither about desktops nor about other apps' windows, so on X11 `x11_stacking.rs` asks the window manager, through x11rb rather than Xlib, whose default error handler would end the process when a window closes during the check: the window is on screen if it's viewable (window managers unmap other desktops' windows), and covered if a normal window above it in `_NET_CLIENT_LIST_STACKING` overlaps it. On Wayland, apps aren't told about other windows, so a window that isn't minimized or suspended always closes. Presenting a window that's on another X11 desktop moves it to the current one (`present_main_window`). The menu's Show Dismas only presents. Scrolling steps the volume (`PlaybackAction::StepVolume`, by `VOLUME_STEP` like the slider). Trays disagree on the direction: Plasma sends Qt's wheel angle (up positive, 120 a notch, less from touchpads), and waybar and others send steps with down positive. ksni hides the one difference in the call ("Vertical" against "vertical"), so `XDG_CURRENT_DESKTOP` containing KDE picks Plasma's way. Upstream snixembed sends no direction (0) and no middle click.
- **Background playback:** while `background-play` is on, the `Application` holds itself, so closing the window keeps the music playing. Closing then only hides the window, which comes back as it was, without a new `Window` reading the albums again; turning the setting off closes a hidden window, so Dismas quits. The hold is taken before asking the Background portal, and only a refusal drops it and turns the setting off. Many sessions have no Background portal (window managers, or a portal frontend with only -gtk, -wlr or -hyprland), and an error there keeps the hold.
- Controllers and the UI ask for things by sending `PlaybackAction`s back to the player.
- `PlayerState` is a GObject whose properties the UI binds to. It is only mutated on the main context.
- `Queue` is the list of tracks to play, a `GListModel` of `Track` GObjects. Shuffling reorders it for real (`Queue::shuffle`), so the order shown, the order played and the order saved are the same. The order is random, but it goes by the play stats (`audio/shuffle.rs`):
  - Each track has a weight, and a track with more weight is more likely to come earlier (Efraimidis and Spirakis's weighted random order).
  - A track heard just now has a tenth of the weight of one never heard, and gets halfway back in a week.
  - A track with 10 plays or more, all time, has twice the weight, so tracks played often but not heard for a while come early.
  - The movements of a work that are next to each other move together, in their order, with the work and composer of the queue's headers as the key (`work_sections::work_key`; see Works below), so each Prelude and Fugue of the WTC moves as one.
  - The same artist (for a movement, its composers) doesn't come twice in a row. The exception is an artist with more tracks than all the others together: its runs are then kept as short as they can be (`Spread`), rather than left to pile up at the end.
- Covers are deduplicated across tracks of the same album through a global `CoverCache`. Each cover has a `OnceLock` slot, so it's decoded once even when several of its tracks load at the same time. The tracks hold the slots (`AlbumCover`), and the cache keeps only weak references, so a cover is freed once no track has it.
- Cover art comes from the tags and could be crafted, so `cover_image.rs` decodes it with glycin, in sandboxed loader processes. Only the decoded pixels are scaled, color-picked and saved as PNG in the app. Decoding blocks, so it never runs on the main thread.
- Tags and covers are read in up to four worker threads: `load_tracks()` (`audio/track.rs`) sends the `TrackData` of each file over a channel, in the order of the files, all the tracks of a file at once (none, one, or a CUE sheet's), and the main thread wraps them in `Track` GObjects, which are not `Send`.
- **Works** (`work_hierarchy_labels` in `audio/track.rs`): a track is a movement when its tags name a work and a movement, and the queue and the album view show a header over the movements of each work (`work_sections.rs`). With the tag of Picard's Work Hierarchy plugin, the work is the top-level one, whichever level the plugin was set to tag, unless a part of it has a catalogue number of its own, one the works above it don't have (`has_own_catalogue_number`). So each Prelude and Fugue of The Well-Tempered Clavier (BWV 846 and on) is a work, but Book I and the acts of an opera aren't. The names of movements often repeat the number of their work, or give it another one ("K359: Variation I" in "12 Variations, K. 374a/359"), so the level a track performs only counts when it has parts (`part_total`): a whole Prelude and Fugue in one track is a work of its own, not a movement. The header shows the work's own name, and Track Information its full title (`work_title`), with the collection. When a movement is in several tracks, MusicBrainz links them all to it and marks the links "partial", so the hierarchy names them the same ("1. Ouverture" for both halves of the Royal Fireworks overture). Those tracks are named after the part of their title after the work instead ("Ia. Overture – Adagio"), with the movement's number in front if the part has none and the movement isn't under an act or part, as opera titles start with the act.
- **CUE sheets** (`cue_sheet.rs`) split an audio file into tracks: a `.cue` file next to it, or a `CUESHEET` tag (a Vorbis comment, or an APEv2 item for Monkey's Audio and WavPack, which `read_tagged_file` reads into `ExtraComments`). A track of a sheet is at a path under the sheet, `Album.cue/track03` (or `Album.flac/track03` for an embedded sheet), which can't be a file, so the queue, playlists, resume points, unshuffled orders and the library keep it like a file's path; `Track::audio_file()` is the file that plays, and `Track::segment()` the part of it. A sheet only splits the files it has two or more tracks in (multi-file rips keep their own tags). The sheet that splits a file is the same however the file was reached: in a list of files, the first `.cue` that splits it (`Claims`), otherwise the first in its folder, otherwise the embedded one. Its tags are the audio file's, minus the ones about the whole file, with the sheet's over them (`album_tag`, `track_tag`), so all the code that reads lofty tags works on them. Sheets in legacy encodings are guessed with chardetng. `load_tracks` reads each sheet and each split file once for all their tracks (`FileCache`). Exported playlists name the tracks the same way, which only Dismas reads. In Flatpak, a `.cue` opened through the document portal from outside the Music folder can't reach its audio file. FLAC's binary CUESHEET block isn't read, only the tag.
- **Playing a part of a file** (`gst_backend.rs`): positions and seeks are relative to the track. A track that doesn't start at 0 only plays once GstPlay says its file is loaded (`TrackLoaded`), as GstPlay drops a seek made before it loads a file; seeks are accurate. When the next track goes on from the end of the current one in the same file, the pipeline plays on, and once the position is past the end the backend sends `TrackAdvanced` (the player confirms it like a hand-over). Otherwise a probe on the audio filter (always set: an identity without ReplayGain) clips the audio at the end and pushes an EOS, so the sink plays the rest and the usual `PlayNext` follows. Only after a track that plays to the end of its file is the next one handed over, and only if it starts at 0. The stream's ReplayGain tags are about the whole file, so a second probe, before rgvolume, sends it the track's gains (from the sheet, or else the file's) as a tag event before the first buffer of each track that reaches the filter, which runs about 2 s ahead of the sink; a tag event only replaces the gains it has. `rgvolume`'s `result-gain` is the gain of the audio passing it, not of what's heard.
- `WaveformGenerator` builds the seek-bar waveform in a separate GStreamer pipeline; for a part of a file, it seeks to it once the pipeline is ready. While `show-waveform` is off, it neither reads the cache nor runs the pipeline.

### UI

- **Composite templates:** each widget is a Rust subclass (`src/*.rs`) bound to a Blueprint template in `src/gtk/*.blp`.
- **Resources:** Meson compiles the `.blp` files to `.ui` and bundles them with CSS and icons through `src/dismas.gresource.xml`. Templates load from `/io/github/dachshund7/Dismas/<name>.ui`.
- **Adding a widget:** update the `.blp` list in `src/gtk/meson.build`, the gresource XML and `po/POTFILES.in` together.
- **Stale resources after editing `.blp` files:** the gresource bundle doesn't track the compiled `.ui` files, so the first `ninja` run can leave the old UI in `_build/src/dismas.gresource`. Run `ninja` a second time.
- **Window coordination:** `Window` is the coordinator. `window.rs` holds its template, properties and `win.*` actions, and its methods are split by area into `window/*.rs`: `bindings.rs` (binding `PlayerState` and the queue to the widgets), `favorites.rs` (the heart button, and marking tracks from their menu), `loading.rs` (opening files, drag-and-drop, restoring the queue), `playlist.rs` (the playlist pane, which shows the queue), `selected_playlist.rs` (selecting, saving, creating, renaming and deleting playlists), `selection.rs`, `albums.rs` (the album grid), `now_playing.rs`, `sidebar.rs`, `sleep_timer.rs` (the sleep timer popover; the countdown itself is `audio/sleep_timer.rs`), `smart_playlists.rs`, `track_menu.rs` and `zen.rs`. Queue search filtering is in `search.rs`.
- **Fitting the window:** sizes come from measuring the content, since they depend on the font DPI. `PlayerBox` (`player_box.rs`) lays out the player and gives the cover the room left: large, medium or hidden. `TrackCover` draws the size it gets as a square. `Window::size_allocate` measures the split view to set the width where `narrow_breakpoint` collapses it, and the window's size request (`window/sidebar.rs`).
- **Settings:** stored through GSettings (`data/io.github.dachshund7.Dismas.gschema.xml`). The main menu only has actions; the settings are in the Preferences dialog (`preferences_dialog.rs`, Ctrl+,), whose switches are bound to their keys, so what depends on a setting watches it or reads it when needed. Its ReplayGain rows go through `win.replaygain`, the window's `replaygain-mode`, which passes the mode on to the player. `move-from-header-bars`: header bars move the window by default, like other GTK apps (on Wayland it's the only way), and turning it off turns off their drag gestures (`utils::set_window_drag`), right away, for window managers that move windows themselves. Empty areas of the content never move the window. `volume` is saved by the player whenever the backend reports a change, and applied at startup, so the slider is right before anything plays (PulseAudio only restores an app's volume when its stream opens, and keeps one it's given); until it has been saved once, PulseAudio's volume stays. `repeat-mode` is saved whenever the queue's mode changes (from the button, the shortcut or MPRIS) and applied at startup. The window's size is saved by `Window::save_window_state`, when the window is closed and in `Application::shutdown`, as quitting doesn't close it. `playlist-visible` is the user's own choice: the pane button, F9, the back button and Esc go through the window's `user-playlist-visible` (the `queue.toggle` action), which stores it, except in the collapsed split view, where the pane only covers the player for a while. The pane opening or closing by itself (added tracks, drops, search, Show the Playing Track, an empty queue) goes through `playlist-visible` and isn't stored. At startup, restoring the queue doesn't open the pane. `show-waveform` (Show Waveform in Preferences) swaps the `WaveformView` for a stock `Gtk.Scale` (`seek_scale`), bound to the setting's visibility; both seek through `Window::seek_to`. `zen-mode` (Zen Mode): with the playlist pane hidden on the player page, `window/zen.rs` waits 3 s once the pointer leaves the window, focused or not (with focus following the pointer, the window keeps the focus when the pointer goes to an empty part of the screen), then fades out the header bar and the `PlayerBox` children with the `player-controls` class, while `PlayerBox::set_zen_progress` moves the cover and the track details to the middle of the toolbar view, under the faded header bar. Only their positions change, not the measured sizes, so the window's size limits stay put. The pointer entering or the window getting the focus (`is-active`) fades the controls in again, for 3 s if the pointer is elsewhere. Whether the pointer is over the window is asked for (`pointer_widget`) rather than taken from `contains-pointer`: when a drag is let go outside the window, GTK puts the pointer back over the window and no leave follows, so moving over the window brings the controls back too. Each step of a resize starts the wait again, as dragging an edge has the pointer outside the window. On touchscreens, a tap (a touch-only `GestureClick`) brings the controls back and starts the wait again. Faded out, the controls and the header bar don't take input (`can-target`), so a tap can't press a button that can't be seen.
- **Fullscreen** (F11, `win.fullscreen`, a property action on GtkWindow's `fullscreened`): everything follows that property, so the window manager's fullscreen does the same (`window/fullscreen.rs`). It goes to the player and hides the pane without storing it, and leaving goes back to the page and the pane from before; the collapsed split view doesn't show the pane again in fullscreen, and leaving hands the pane to `sidebar_visible_uncollapsed` if the window is collapsed by then, as the window and the breakpoint can change in either order. The `fullscreen` class on the player's `CoverBackdrop` (`cover_backdrop.rs`) makes it larger and always dark, in white over a scrim, and the header bar only has a Leave Fullscreen button. Without a compositor, libadwaita keeps the padding of the window's frame (`window.solid-csd`) in fullscreen, which the stylesheet takes off, as it showed as a light border. The backdrop is the shared cover, blurred small once per cover in another thread (`CoverImage::backdrop`) and scaled up, rather than a blur node, which the renderer could blur again over the whole screen whenever the waveform redraws. Zen Mode's fading applies in fullscreen whatever the setting, once the pointer stays still for 3 s (a motion that doesn't move counts for nothing, as X11 sends some), except while the sleep timer, the more menu or a dialog is open; the pointer hides with the controls. The window's size limits aren't measured in fullscreen, as the larger player would raise the size the window goes back to. Esc leaves fullscreen after leaving selection mode and hiding the pane.
- **Match Cover Art** (`enable-recoloring`): `update_style` (`window/now_playing.rs`) writes the cover's palette as `--background-color-N` on `:root`, and the stylesheet makes tints of them in OKLCH, keeping their hue and a little of their chroma at a lightness set by the color scheme, so the text keeps the theme's contrast. The accent color comes from the most chromatic color, counting less the less of the cover it covers (`cover_image::accent_color`), and is worked out once per cover (`CoverArt::accent`). The share of each color is measured (`CoverImage::shares`), as color-thief orders its palette by pixels times the range of colors, not by coverage. To tune it on real covers, the ignored test `print_palettes` (`audio/cover_cache.rs`) prints the palettes of a music folder. The accent color is behind the `cover-accent` class, since an undefined variable would make the accent color invalid rather than fall back to the system's. High contrast turns it off.
- **The library** keeps a row per track, with the file it comes from (`file`: the track's own, or the `.cue` or image of a sheet); the scan compares the time and size of each file (a `.cue`'s include its audio files'), and reads a changed file's tracks again together. Tracks without an album tag are grouped by the folder they're in (`album_folder`, where disc folders count as their parent), as an album named after it (`folder_album_title`), which `Track::album` shows too, and searches. Hidden files and folders aren't read (a drive's `.Trash-<uid>` keeps deleted tracks under their names), nor `$RECYCLE.BIN`.
- **Music folders** (`music-folders`, edited in Preferences): an `a(ss)` of URIs, the folder that's read and, for one that came through the document portal, its host path, which names it and tells it apart even once the portal can't (access taken back, or the folder made again, which gives it a new doc ID). An empty list means the XDG Music folder (`library::music_folders`). In Flatpak, the portal gives a folder picked in ~/Music a doc path too, as it grants write access and the manifest only has `xdg-music:ro`; `resolve_folder` reads it through ~/Music instead, spelled like ~/Music so its tracks keep their paths. Folders are compared by `folder_key` (the host path, or the path without symbolic links), and `roots` leaves out those inside another. A folder that's missing or empty (often a drive that isn't mounted) is unavailable: its tracks are kept, so they aren't read again when it's back, but hidden, as they can't play (`albums` and `search_albums` take the hidden folders, which `LibraryView::reload` works out), and covers are only made from the tracks that are there, so theirs aren't lost. Removing a folder only changes the album grid: the queue and playlists are lists of files, so they keep its tracks, which the Remove toast says when the selected playlist has some. The library is read again when the Preferences dialog closes, if the folders changed (a scan can't be stopped, so a folder added by mistake isn't read); a scan asked for during another follows it (`rescan_pending`). A hand edit with `gsettings` applies at the next scan.
- **Playlists:** one playlist is selected at a time (the `selected-playlist` setting, empty for the queue). Its tracks are loaded into the player's single `Queue`, which plays them and receives added tracks. Switching stops playback and reloads the `Queue` from the other playlist's file. All playlists are M3U8 files written and read by `playlists.rs`, in the order of their tracks: the queue is `~/.local/share/dismas/queue.m3u8`, and saved playlists are in `~/.local/share/dismas/playlists/`. Shuffling reorders the selected playlist and saves it, keeping the order from before in `~/.local/share/dismas/unshuffled/` (`queue.m3u8`, and `playlists/<name>.m3u8`, so a playlist named "queue" has its own) until the shuffle button is turned off, which puts it back by URI, with the tracks added since at the end. The button shows whether that file exists, for the selected playlist: it's synced from it (`sync_queue_shuffled`) on switching playlists and when the queue empties, and only the button and its shortcut go through the `queue-shuffled` setter, which shuffles or restores. The playing track, or one paused partway, stays first; otherwise the first shuffled track is made current. The file is written before the shuffled playlist, and removed after the restored one is saved, so a crash can't lose the order. It follows renames, goes with deletes, is copied by Save as Playlist, and is dropped when the tracks are replaced (Remove All, the Play buttons, playing dropped files, files opened at startup); the toast's Undo puts the queue's back. They're listed on the Playlists page (`playlists_page.rs`). Importing reads any M3U file, resolving relative paths against its folder and keeping only the tracks found. Exporting writes paths relative to the folder of the file for the tracks under it, so the playlist can be copied with the music to another device. Files dropped on the window go by where they're dropped. A single drop target, on the window's drag overlay (`drag_overlay.rs`), takes them all and works out at each motion what a drop there would do (`file_drop_at` in `window/loading.rs`): on X11 the widgets aren't told the drag left once it's dropped, so a second target that took the drag without getting the drop would keep it and turn the next one down. On the playlist pane, the files go between the tracks where the reordering line shows, or at the end where there's none (on the album's tracks), which the pane's outline shows. Above the first movement of a work, which would be under its header, they go before the work: the line is under the row before it, or above the header of the work at the top. Elsewhere, the overlay shows two zones over the main area: a large one that adds the tracks to the selected playlist, and one below it that plays them in place of the queue, like an album's Play button, with an Undo on the toast that puts back the queue and the playlist that was selected (`undo_replace`). The zones are laid out beside the pane, over the part of the main area that shows: next to the sidebar of the collapsed split view, the content is only drawn moved aside (`PushBin`). There's no modifier key for playing, as the app the files are dragged from reads the keys, and on Wayland Dismas can't see them. Albums are dragged from the grid the same way (`setup_album_drag` in `library_view.rs`), a selected one in selection mode taking the other selected ones, as an `AlbumDrag` that only Dismas takes; they only go to the pane, which is shown while they're dragged if it was hidden, and hidden again if they aren't dropped. Esc cancels the drag, as for tracks, through `utils::cancel_drag`. On X11 without a compositor, the window's input shape is set to its size after each resize (`setup_x11_drop_shape`): GTK's X11 drag sources cache the shapes of the windows, and a window without one never tells them it grew, so drags over the part added by widening the window went to the window below.
- **Smart playlists** (Recently Played and Most Played, on the Playlists page) come from the play stats (`play_stats.rs`), in `~/.local/share/dismas/plays.db`. It's a database of its own because the library's is a cache whose schema bumps drop the tracks, and the history can't be read again from anywhere: its tables are never made again, a later version only changes them in place, and a version newer than the build knows is left alone. The player's `ListenTracker` measures each listen from the positions it's given (whole seconds, four times a second): a step of 1 or 2 s while playing is heard, and anything else (seeks, resume points, going back) only moves the last position. `show_track` ends the listen and starts one for the new track, `clear_current_track` ends it, and so does the end of the queue. Ending keeps the track, so playing it again without `show_track` (`start_over` on a one-track queue, or Stop then Play) is a new listen. A listen is logged from 30 s, or half of a shorter track, and counts as a play (`counted`) from half the track or 4 minutes, whichever is less, as on Last.fm. A track of unknown length needs 30 s and 4 minutes. Listens are written in GLib's pool when they end. On quitting, and before a smart playlist is read, the listen to the track playing is written right away (`save_listen`), so that it's saved, and on the list. Each write adds to the track's all-time `totals` (plays, seconds heard, last played) and drops the listens older than a year. Tracks are told apart by their URI, so a moved file starts again. Recently Played is the last 100 tracks logged, played oldest first, in the order they were last heard, so that a work's movements keep their order; Most Played is the 100 with the most plays in the last 182 days; tracks with the same number of plays are in the order they were last heard, so that a work heard through keeps its movements in order too. Opening one reads the list from the database at that moment, as a snapshot that doesn't change afterwards, and plays it in place of the queue, like dropped files (`play_in_place_of_queue`), with the same Undo, so it's never the selected playlist. Shuffling reads the stats too: each track's all-time plays and when it was last heard (`track_stats`, from `totals`), on the main thread, as the shuffle also saves the playlist there. There's no way yet to clear the history or turn it off. **Favorites** are in `plays.db` too, as they can't be read again from anywhere either: the `favorites` table, added in schema version 2 (the `CREATE TABLE IF NOT EXISTS` of the schema adds it to a version 1 database), keeps each track's URI and when it was marked. The heart button right of the Sleep Timer (`win.favorite`, a property action on the window's `track-favorite`), Ctrl+D and the track menu mark and unmark them; the heart is filled and red, whatever the accent color. `sync_track_favorite` reads whether the playing track is one each time the track changes. They're read and written on the main thread, as each is a single row; if they were written in GLib's pool, like the listens, two clicks close together could be written in the wrong order. Favorites, on the Playlists page, plays them like the smart playlists, in the order they were marked, so that the movements of a work marked one after another keep their order.
- **Pages:** the player, the album grid and the Playlists page take turns in the main area. Each header has the same `PageSwitcher` (`page_switcher.rs`), whose buttons drive the window's `page` property through the `win.page` action. Its playlist pane toggle sits on the left, apart from the page buttons. Its Player button follows `player-available`, which is false while there is nothing to play. Where a header bar is too narrow for the page buttons, the switcher folds them into a menu button during allocation (`set_child_visible`), and measures only the folded width as its minimum; the page titles are in a `FitBin` (`fit_bin.rs`), which hides its child where it doesn't fit. With the album grid's single column, that keeps every page within the 360-pixel minimum, whatever window buttons the desktop shows.
- **Restoring at startup:** a selected saved playlist always reopens. "Restore Queue at Startup" (the `restore-playlist` key, named after Amberol's) only decides whether the queue keeps its tracks; without it, the queue starts empty. Opening Dismas with files replaces the queue. A reopened playlist resumes, paused, from its point in the `resume-points` setting (`resume_point.rs`), and so does a playlist switched back to: by playlist name, the track's URI and its index in the order the tracks were added, and the position. The `Application` saves the selected playlist's point, since it outlives the window, when playback pauses, stops or changes track, when the queue changes, every 30 s while playing, and on quitting (SIGTERM quits too). Switching saves it right away, in `replace_selected_playlist`, as the save at idle would come after the switch. Renaming a playlist moves its point, deleting drops it, and startup drops those of playlists that are gone. Resuming shows the track paused without getting the pipeline ready: `GstBackend::resume_at` keeps the position and seeks when the track plays. A pipeline prerolled to PAUSED that only starts playing a few seconds later stays stuck at its position with PulseAudio.
- **Command line** (`Application::command_line`, with `HANDLES_COMMAND_LINE`): the first Dismas gets the arguments and switches of each `dismas` run, with relative paths resolved in the folder it was run in. Plain files go to `open`, which D-Bus Open from file managers uses too: at startup they replace the queue, and in a running Dismas they're added to the selected playlist, bringing up the window. `--add` adds them to the end of the selected playlist without bringing up a window that's there, hidden or not, and leaves the page and the pane as they are (`QueueMode::Quiet`), so scripts can add tracks while the user does something else. `--play` plays them in place of the queue, like the drop zone (`play_in_place_of_queue`, with its Undo). If Dismas isn't running, both start it by restoring the selected playlist, and then wait until the playlist's tracks are in the queue (`Window::after_startup`): tracks are read in other threads, so tracks read while the playlist loads would land in the middle of it, and the playlist would be saved without its own tracks. Giving both switches is turned down in `handle_local_options`, in the process that was run.
- **Migrating from Amberol:** on the first run (no library, queue or playlists in `~/.local/share/dismas` yet), `migrate.rs` copies them from `~/.local/share/amberol`, and copies the settings changed in the `io.bassi.Amberol` schema if it's installed. Caches aren't copied; they're made again.

### Translations

- UI strings use gettext helpers from `src/i18n.rs` in Rust, and `_()` / `C_()` in Blueprint.
- `po/*.po` files came from upstream's translators (GNOME's Damned Lies). Don't rewrite them wholesale; when a source string changes, keep the edit to the affected entries. Translations that couldn't follow the rename from Amberol are marked fuzzy. New translatable files go in `po/POTFILES.in`.

## Conventions

- Commit messages: a one-sentence summary line of at most 72 chars, capitalized, with no trailing period. Then a blank line and a prose body explaining *why*. Use `Closes #N` / `Fixes #N` for issues.
- The UI calls audio files "tracks" (not "songs"). Keep the freedesktop icon name `media-playlist-repeat-song-symbolic` as is.
