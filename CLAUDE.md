# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Upstream policy on AI contributions

This repository is a fork. The upstream project (gitlab.gnome.org/World/amberol) **does not accept contributions generated by LLMs**, and its contribution guide names Claude explicitly. This covers code, docs, issues and artwork. This fork's own CONTRIBUTING.md welcomes AI-assisted work, but none of it goes upstream. Don't prepare merge requests, issues or other upstream submissions from AI-generated work.

Flathub has a similar policy (the Generative AI policy in docs.flathub.org's requirements): a Flathub manifest must not contain AI-generated or AI-assisted content, AI tools must not open a submission or write its description, commits or replies, and AI-generated code in the app must be disclosed. Don't write a Flathub manifest or prepare a Flathub submission. The manifests in this repository are for building the app outside Flathub.

## Build and run

Dismas is a GTK4/libadwaita music player written in Rust, forked from Amberol. The app ID is `io.github.dachshund7.Dismas`. Build it with Meson, which runs Cargo itself. A plain `cargo build` fails until Meson has generated `src/config.rs`.

```sh
meson setup _build                     # add -Dprofile=development for a debug build with the .Devel app ID
meson compile -C _build                # or: ninja -C _build
meson devenv -C _build ./src/dismas    # run uninstalled
```

- **Generated `config.rs`:** `meson setup` writes `src/config.rs` from `src/config.rs.in` and copies it into the source tree. The file is gitignored. Cargo, rustfmt and clippy all need it to exist.
- **Profiles:** the default profile builds `--release`. Cargo's target dir is `_build/src/`. `Cargo.toml` has no release profile of its own, so a local release build rebuilds in about 25 s and keeps its symbols, which perf needs; the builds that are shipped, the tarball and the Flatpak, set `CARGO_PROFILE_RELEASE_LTO` and `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1` themselves, for a smaller binary. Development builds log Dismas's debug messages, and release builds its messages from info up; `RUST_LOG` (e.g. `dismas=debug`), when set, replaces that default rather than adding to it, as a setting for `dismas` would take precedence over a general one like `RUST_LOG=debug`.
- **Installed data** (`data_paths` in `main.rs`): the resource bundle and the translations are looked for next to the binary first, as `<prefix>/share/dismas/dismas.gresource` and `<prefix>/share/locale` are to `<prefix>/bin/dismas` (with symbolic links resolved), and then at the paths Meson built in (`PKGDATADIR`, `LOCALEDIR`), which for a Meson install are the same. So a build unpacked anywhere runs. A compiled schema in `<prefix>/share/dismas/schemas`, which only the prebuilt tarball has, is put in front of `GSETTINGS_SCHEMA_DIR` before anything reads a setting. Under `meson devenv`, the bundle is next to the binary in `_build/src`.
- **Runtime dependencies:** gtk4 ≥ 4.19.5, libadwaita ≥ 1.8, GStreamer ≥ 1.20 (incl. plugins-bad), and the glycin loaders (`glycin-loaders`, plus `bwrap` outside Flatpak) to decode cover art. At build time: `blueprint-compiler`, `msgfmt` (gettext), the SQLite development files for the library database (rusqlite links against the system SQLite), and the libseccomp and fontconfig development files, which glycin links against.
- **Flatpak:** there are two manifests, which differ only in the app ID, the profile and the variables of each profile (the regular one's LTO, the Devel one's debug ones); keep the rest the same. `io.github.dachshund7.Dismas.json` builds the regular one, which the releases ship, and `io.github.dachshund7.Dismas.Devel.json` the Devel one, which CI builds on each push. With their own app IDs, the two can be installed side by side. Both build on the GNOME 51 runtime from the folder they're in (a `dir` source, skipping the build folders), and let Cargo download the crates during the build (`--share=network`). They read the Music folder through both `xdg-music:ro` and `~/Music:ro`: where no `~/.config/user-dirs.dirs` sets `XDG_MUSIC_DIR`, as in many window manager sessions, `xdg-music` shares nothing, while Dismas falls back to `~/Music` (`library::default_music_dir`). A file that came through the document portal (opened, dropped, or in a music folder added outside the Music folder) has a path under `/run/user/<uid>/doc/` in the sandbox, and its path outside it (`utils::ATTRIBUTE_HOST_PATH`) only names it: Open Directory (`open_containing_folder`) gives `gtk::FileLauncher` the sandbox path, as the launcher opens the file and the portal works out its folder outside, while the host path can't be opened inside the sandbox. The album menu's (`open_album_directory`) selects the album's first track, its sheet, or the folder of its first disc (`library::album_folder_entry`), which gives the portal a folder rather than a file. Inside the sandbox, the data is under `~/.var/app/<app ID>/`, so there's nothing to migrate from Amberol.
- **Prebuilt tarball** (`build-aux/make-tarball.sh`): a release build installed to a staging folder with `--prefix=/usr/local`, laid out as `dismas-<version>-<arch>/` with `bin/`, `share/`, `install.sh`, `README.txt` and `COPYING`, which runs from wherever it's unpacked (see Installed data). The schema is compiled in `share/dismas/schemas` rather than `share/glib-2.0/schemas`, where a compiled schema unpacked into `~/.local` would replace the other apps' ones. The binary is built with LTO and one codegen unit, and stripped (`CARGO_PROFILE_RELEASE_STRIP`), as Meson's install doesn't strip Cargo's output; flatpak-builder strips the Flatpak's itself. It links the system's GTK, libadwaita and GStreamer, and the script fails if the binary needs a newer glibc than `MAX_GLIBC` (2.41: Void's, the oldest of the distributions with GNOME 49's libraries). It needs 2.39, for the `pidfd_spawnp` of Rust's standard library. Run locally, it builds in `_build-tarball` and puts `src/config.rs` back afterwards, as `meson setup` copies its own over it. `build-aux/install.sh`, shipped as `install.sh`, adds it to the current user's menu: a link `~/.local/bin/dismas`, the desktop file and the D-Bus service with that link's path in `Exec` (the desktop file is `DBusActivatable`), and links to the app icon and its symbolic one, which the menu and the tray look up by name. It only replaces links into a prebuilt Dismas, dangling links and files with its mark, so it stops at a build from source installed in `~/.local`, which has the same files, and `--uninstall` removes only those.

## Checks

GitHub Actions (`.github/workflows/ci.yml`) runs these on pushes to main and on pull requests. The `lint` job runs `checks.sh` and `reuse` on Ubuntu. `.github/workflows/advisories.yml` checks Cargo.lock against the RustSec advisory database (`cargo deny check advisories`, set up in `deny.toml`) on the pushes to main and the pull requests that change Cargo.lock, `deny.toml` or the workflow, and on main every day, as a new advisory can fail it without a change to the code; a failed scheduled run is emailed to whoever last changed its `cron` line, and GitHub turns the schedule off after 60 days without activity in the repository. The `build` job builds the app with Meson and runs clippy, the tests and the data file validation in a `fedora:latest` container, because Ubuntu's GTK and libadwaita are too old, and then fails if they changed Cargo.lock: they run Cargo without `--locked`, so a Cargo.toml change committed without its Cargo.lock would otherwise build from a lockfile that isn't the committed one, which `cargo deny` doesn't check. The `flatpak` job builds the Devel manifest in the `ghcr.io/flathub-infra/flatpak-github-actions:gnome-51` image and uploads `dismas-devel.flatpak` as an artifact. `.github/workflows/release.yml` builds the regular manifest the same way when a version's tag is pushed (`20*`), and its `tarball` job builds the prebuilt tarball with `make-tarball.sh` in `fedora:latest`. Its `draft` job then puts `dismas.flatpak` and the tarball in a draft release, which is checked and published by hand (RELEASING.md), as files can't be added to a published release once it's immutable. The draft's notes are the version's section of CHANGES.md at the tagged commit, which it reads through the API (an rc tag, like `2026.11-rc1`, takes its version's), as the notes of 2026.10 were; a tag's message would lose the change log's `###` headings, which `git tag` strips as comments. Run by hand, the workflow only builds them, in the artifacts of the run. Only the `draft` job can write to the repository: the builds run the build scripts and macros of every crate, so they get a token that only reads, and the `draft` job runs none of the repository's code, only `gh` and GitHub's own actions. The checkouts don't keep the token in `.git` (`persist-credentials: false`). The workflows pin their actions to commits, with the release each one is in a comment, as a tag can be moved to other code: release.yml's `draft` job can write to the repository, and the jobs of ci.yml and advisories.yml on main can save to its Actions cache. Update them by hand, in all the workflow files together, at the start of each cycle, with the crates (RELEASING.md's Dependencies, which also says what to do when the Advisories workflow fails); there's no Dependabot, as its pull requests would land on main between releases. The `lint` job installs Rust with the runner's own rustup rather than an action, as `dtolnay/rust-toolchain` has no releases to pin to, only a branch for each toolchain. release.yml's `flatpak` job also turns off the flatpak-builder action's cache (`cache: false`, and `restore-cache: false`): the cache holds what the runs of ci.yml on main saved, and those runs also run code that isn't pinned, such as the `fedora:latest` and `gnome-51` images and the `fsfe/reuse:6` image that the REUSE action builds from, which all move, so that code could put its own build into the release. To try the `build` job locally, run its commands in `podman run fedora:latest`; the `flatpak` job, with `flatpak-builder` in that image (`podman run --privileged`).

```sh
cargo fmt --all -- --check                  # needs src/config.rs; a blank line is enough (CI writes one)
cargo clippy --all-targets -- -D warnings   # keep it free of warnings
cargo test                                  # unit tests are in #[cfg(test)] modules next to the code
cargo test <name>                           # a single test
build-aux/checks.sh                         # fmt, typos (configured in .typos.toml), POTFILES.in, resource order
reuse lint                                  # REUSE/SPDX licensing; needs reuse ≥ 4, older ones ignore REUSE.toml
cargo deny check advisories                 # the dependencies against the RustSec advisories
```

Every source file needs SPDX headers (`SPDX-FileCopyrightText` / `SPDX-License-Identifier`). REUSE.toml covers files that can't carry headers.

## Architecture

### Audio: message passing between threads

`src/audio.rs` has a header comment explaining the design. GStreamer and the controllers can fire from other threads, so nothing touches the UI state directly. Everything goes through async channels:

- `AudioPlayer` (`audio/player.rs`) is the hub. `Application` (`application.rs`) owns it and gives it a sender for `ApplicationAction`s.
- `GstBackend` wraps GstPlay and reports changes over a channel.
- Gapless playback goes around GstPlay, whose `set_uri` stops the pipeline. The player publishes the next track (`update_next_track`), as a `TrackSource`: the track's URI, which tells tracks apart, and the audio file's, which plays. On playbin's about-to-finish, the backend hands it to playbin, one track at a time. On stream-start it sends `TrackAdvanced`, and the player follows without touching the pipeline. Without a hand-over, EOS leads to `PlayNext` as before. GstPlay changes the pipeline's state and loads tracks on its own thread, and stopping or starting it while a track is handed over can hang GstPlay, so the hand-over is skipped while the playbin's state lock is held, while a load is pending (counted until each `uri-loaded`), within 500 ms of the last load (rapid skipping), and for a file with a video stream (`TrackSource::video`, which only GStreamer's Discoverer sets, through `FileDetails`): GstPlay turns the video off by selecting each file's streams, and decodebin3 never applies the selection for a file handed over, so the pipeline stopped for good a second before the end of the track before. A generation number lets the player ignore switches from before it loaded a track. `stop` loads the track again, since uridecodebin3 would keep a track that was handed over. rgvolume only resets on EOS, so the ReplayGain bin sends it an EOS of its own at each stream-start and drops it after rgvolume.
- Controllers implement the `Controller` trait (`audio/controller.rs`) and are pushed state changes by the player:
  - `MprisController`: media keys and desktop integration. GNOME Shell and Plasma show only the title and `xesam:artist`, so the artists are `Track::credited_artists`: the artist tag, then the names Copy adds to it (`TrackData::credited_artists`: the performers after a composer, or the composers of classical music, as `copied_details`), and nothing for other music. The artist tag stays first, as scrobblers like rescrobbled take only the first artist. The tray's tooltip names the same artists. The metadata also has the composers, the album artist, the lyricists, the genres, the track and disc numbers, the date `year()` comes from (`year_date`, up to a '/' of a range), and the audio file's URI (`audio_uri`, as a CUE track's own isn't a file). Not the favorites as `userRating`, which would need a hook to follow marking, nor the plays or the lyrics, which would be read at each change of track.
  - `InhibitController`: prevents suspend during playback.
  - `TrayController` (Linux/FreeBSD): a StatusNotifierItem through ksni, which runs on a thread of its own, so the tray sends `ApplicationAction`s (`ToggleWindow`, `Present`, `Quit`) and `PlaybackAction`s. It's shown while `background-play` is on, and waits for a tray host if there's none yet. Its icon is the app icon, by the app ID, which Flatpak exports to the host, where the tray looks it up. Clicking it closes the window if it has the focus, or if it's on screen and nothing covers it (with focus following the pointer, moving to the tray focuses other windows), and presents it otherwise (`closes_on_click` in `application.rs`). GTK knows neither about desktops nor about other apps' windows, so on X11 `x11_stacking.rs` asks the window manager, through x11rb rather than Xlib, whose default error handler would end the process when a window closes during the check: the window is on screen if it's viewable (window managers unmap other desktops' windows), and covered if a normal window above it in `_NET_CLIENT_LIST_STACKING` overlaps it. On Wayland, apps aren't told about other windows, so a window that isn't minimized or suspended always closes. Presenting a window that's on another X11 desktop moves it to the current one (`present_main_window`). The menu's Show Dismas only presents. Scrolling steps the volume (`PlaybackAction::StepVolume`, by `VOLUME_STEP` like the slider). Trays disagree on the direction: Plasma sends Qt's wheel angle (up positive, 120 a notch, less from touchpads), and waybar and others send steps with down positive. ksni hides the one difference in the call ("Vertical" against "vertical"), so `XDG_CURRENT_DESKTOP` containing KDE picks Plasma's way. Upstream snixembed sends no direction (0) and no middle click.
- **Background playback:** while `background-play` is on, the `Application` holds itself, so closing the window keeps the music playing. Closing then only hides the window, which comes back as it was, without a new `Window` reading the albums again; turning the setting off closes a hidden window, so Dismas quits. The hold is taken before asking the Background portal, and only a refusal drops it and turns the setting off. Many sessions have no Background portal (window managers, or a portal frontend with only -gtk, -wlr or -hyprland), and an error there keeps the hold.
- Controllers and the UI ask for things by sending `PlaybackAction`s back to the player.
- `PlayerState` is a GObject whose properties the UI binds to. It is only mutated on the main context. Positions come from the backend to the millisecond (`PlaybackAction::UpdatePosition`, about four times a second, GstPlay's interval of 250 ms), which `position_time()` gives; the `position` property, the controllers, the listens and the resume points go by whole seconds. Seeks are to the millisecond too (`seek_position_abs`, MPRIS SetPosition, a click on the waveform), and so is where a track that hasn't played yet will start (`start_position`).
- `Queue` is the list of tracks to play, a `GListModel` of `Track` GObjects. Shuffling reorders it for real (`Queue::shuffle`), so the order shown, the order played and the order saved are the same. The order is random, but it goes by the play stats (`audio/shuffle.rs`):
  - Each track has a weight, and a track with more weight is more likely to come earlier (Efraimidis and Spirakis's weighted random order).
  - A track heard just now has a tenth of the weight of one never heard, and gets halfway back in a week.
  - A track with 10 plays or more, all time, has twice the weight, so tracks played often but not heard for a while come early.
  - The movements of a work that are next to each other move together, in their order, as the queue's headers group them (`work_sections::continues_work`; see Works below), so each Prelude and Fugue of the WTC moves as one.
  - The same artist (for a movement, its composers) doesn't come twice in a row. The exception is an artist with more tracks than all the others together: its runs are then kept as short as they can be (`Spread`), rather than left to pile up at the end.
- **Play Next** (`Window::play_next` in `window/adding.rs`, from the track menu, the album menu and the Add buttons) puts tracks before `Queue::play_next_before`: after the current track and the tracks after it that continue its work (`continues_work`), so a work isn't cut, then after the tracks Play Next put in that follow those (`played_next`, weak references), so tracks played next one after another play in the order they were chosen; with no current track, at the start. Any other track in between ends that run, so dragging tracks between them, or one of them further down, can't push the place below the playing track. The tracks put in are forgotten on a jump (`skip_track`, `previous_track`, `clear`), and kept by `next_track`, which the end of a track, the gapless hand-over and Next go through. A sort forgets them too, as they're no longer after the current track. Files are placed once they're read (`Place::Next` in `LoadOptions`), as playback can move on meanwhile. Tracks of the queue are moved instead (`move_to_play_next`), without the playing one. In a shuffled playlist, they go to the end when the order from before is put back, like any track added since.
- **Sorting** (`audio/sort.rs`; the sort button at the start of the pane's header, whose menu's items are `queue.sort` with a `SortKey` as the target): Album, Artist, Composer, Title, Year and File Name sort the selected playlist's tracks once (`Queue::sort`, in one splice, the current track staying current) and save them, and Reverse Order turns their order around. Nothing stays sorted, so dragging, Play Next and added tracks work as before. The movements of a work that are next to each other move as one unit, in their order, as in the shuffle (`shuffle::work_units`), and a unit goes by its first track, so Title sorts it by the work's name, as its header shows it. Tracks that go in the same place are put in the order of their albums (`AlbumOrder`): by the album's title, those without one last, then by the album artist, then by what tells apart albums with the same title and album artist, as the library's `album_id` does (the release id, or else, for an album without its title or its album artist, its folder, so that two compilations named "Greatest Hits" don't interleave), and then by `TrackOrder`, the album pane's order; tracks still in the same place keep the order they had. Artist goes by the ARTISTSORT tag, or else by the artist as written, as working out a last name would turn bands around. Composer goes in the Works page's order (`library::work_orders`, which `sort_works` uses too): the first composer's sort name (COMPOSERSORT, matched to the composers by name, or else one worked out, `credited_work_composers`), then the composers, then the catalogue number in the composer's main catalogue, counted once per work, as a playlist can have several recordings of one, then the name; tracks without composers go last, in the order of their albums, as missing values do in the other sorts. Both sort names are on `TrackCredits` (`artist_sort`, `composer_sorts`). Year is the oldest first, and File Name goes by the file's name, a CUE track by its sheet's name and then its number, worked out from the path alone. `Track::sort_entry` gives what a sort knows of a track, under one borrow of its tags; `Queue::sort` asks it only of the first track of each unit, as the sort reads nothing else of the others, and of none for Reverse. `Window::sort_queue` (`window/selected_playlist.rs`) makes the first track current, as shuffling does, unless a track is playing or paused partway, and turns shuffle off for a shuffled playlist, dropping its order from before shuffling once the sorted order is saved. The Undo of its toast, which Ctrl+Z presses (`undo_sort`), puts back the tracks themselves rather than their URIs (`Queue::restore_tracks`), so that copies of a file go back to their own places, with the order from before shuffling, and the track that was current, if nothing has played since; the tracks added since go at the end. The toast (`sort_toast`) is dismissed when the queue's generation changes and when shuffle is turned on or off, as the order it would put back is no longer the one before the last change. A sort that changes nothing says so in a toast of high priority, which shows at once rather than after the toast of the sort before, whose Undo comes back after it; Reverse on a playlist that's a single work says that its movements stay in their order. Afterwards the pane shows the playing track, or else its top, with the header of the first work (`show_queue_after_reorder`).
- **Undoing removals** (`Window::remove_tracks` in `window/playlist.rs`): removing tracks from the queue shows a toast whose Undo puts them back, and so does Remove All (`remove_all_tracks`), which removes the whole queue as one run. `Queue::remove_tracks` returns each run of tracks that were next to each other, with the tracks that came right before and right after it (`RemovedRun`), as a position wouldn't hold once other tracks were added, moved or removed. `Queue::put_back` puts a run before the track after it, or else after the track before it, so that tracks added since at the end stay after it; the whole queue goes back before the tracks added since. Tracks removed while the toast is up add to it (`QueueUndo`, in `queue_undo` while its toast is up), and the last removed go back first, so that a run finds its track even when that track was removed after it. The queue's `generation` goes up each time it's emptied for other tracks (`Queue::clear`: switching playlists, Remove All, playing tracks in place of the queue), which dismisses the toast, as the tracks would otherwise go back among another playlist's. They come back unselected, as tracks removed in selection mode keep their selection. Playback stays where it is, unless removing emptied the queue: then the player page, if it showed, the pane and the track that was playing, paused where it was, come back too, which `take_queue_undo` keeps before each removal. Removing the selected tracks (`remove_selected_tracks`: the selection bar's Remove, Delete, and the track menu on a selected track) leaves selection mode, as nothing selected is left. When the focus is on a removed track, on the bar's Remove button, which leaving selection mode hides, or nowhere, as once the track menu closed, `remove_tracks` gives it to the first track shown after the focused one, or after the first removed, that stays, or else to the one before (`track_after_removal`), as GTK put it on the first row of the list.
- **Stopping after the track or the work** (Stop After This Track and Stop After This Work, at the top of the sleep timer's popover; the second only while a movement plays): they're toggle buttons of one action, `win.sleep-timer-stop-after` with the target "track" or "work", whose state is the end the timer waits for, so the one waiting is highlighted in the accent color, like the moon button, and a click on it turns it off; the line at the top of the popover only shows the time left while the timer counts down. Whether they can be used follows the playing track (its `track` notifications), not the opening of the popover, as the queue can load while it's open. `SleepTimer::stop_at_end` sets what the timer waits for (`waiting_for`, a `TimerEnd`) to the track, as once it ran out with Finish Last Track, or to the work. The player's `stops_at_track_end` says whether the music stops at the end of the current track: always while finishing the track, and while finishing the work when the next track doesn't continue it (`continues_work`, on the queue's current and next tracks, as the queue goes on before the state shows it). While it's true, the next track isn't handed over gaplessly (`update_next_track`, which the notifications of `waiting_for` call again), so the movements of the work still follow each other without a gap. At the end of the track, `play_next` turns the timer off and pauses at the next track, so that playing again starts there; a failed track ends it the same way (`after_failure`). When no track is left playing, as when the queue is emptied or another playlist is selected, `clear_current_track` turns off waiting for the end (`SleepTimer::track_gone`), as the track it was for is gone; a countdown goes on. Going to another track keeps it.
- Covers are deduplicated across tracks of the same album through a global `CoverCache`. Each cover has a `OnceLock` slot, so it's decoded once even when several of its tracks load at the same time. The tracks hold the slots (`AlbumCover`), and the cache keeps only weak references, so a cover is freed once no track has it.
- Cover art comes from the tags and could be crafted, so `cover_image.rs` decodes it with glycin, in sandboxed loader processes. Only the decoded pixels are scaled, color-picked and saved (as PNG, or as JPEG for the album grid) in the app. Decoding blocks, so it never runs on the main thread. A cover file next to the tracks over 32 MiB isn't read (`read_cover_file`), and the read itself stops past that size, as a file of procfs or sysfs, which a symbolic link among the covers can lead to, doesn't hold the size it reports: `/proc/self/pagemap` reports 0 bytes and holds hundreds of gigabytes.
- **Tracks:** `audio/track.rs` has `TrackData`, the tags and file details of a track, and `Track`, the GObject the lists show; `audio/track/` has the rest: `credits.rs` (`TrackCredits`, and how the performers and composers are shown), `search.rs` (the text searches look into, without the times and header lines of synchronized lyrics, `lyrics::text_without_times`, which searching for a number would match), `tags.rs` (`read_file_tags`, the only way a file's tags are read, which gives `FileTags`: the tag a file's tracks take, the same in the queue, the library and the covers, with `ExtraComments`, the file's properties and its format), `lofty_gaps.rs` (what lofty leaves out of a tag where it has an `ItemKey` for it; see below), `discovered.rs` (the files lofty can't read, read with GStreamer; see below), `work_hierarchy.rs` (the Work Hierarchy plugin's tag), `file_name.rs` (titles and albums from file and folder names) and `loader.rs` (`load_tracks`, and reading the tracks of a file).
- **lofty's gaps** (`audio/track/lofty_gaps.rs`): where lofty reads an item wrongly or leaves it out of the tag though it has an `ItemKey` for it, a fill (`Fills`) adds it to the tag under the key lofty uses for the other formats, so the code that reads the tag never knows, and only if the tag has none of that key, so a lofty that reads it itself makes the fill do nothing. The tags lofty has no key for at all go in `ExtraComments`. Each gap has a canary test (`still_…`) that fails once lofty fills it, and says what to delete; another fails once lofty reads a file type it couldn't (`still_unread_file_types`), whose files GStreamer reads until then, as `FileType` is non-exhaustive and a new type would go to the `_` arm of `read_tagged_file`. **Upgrading lofty:** run `cargo test lofty_gaps` and follow the messages of the tests that fail.
- **Files lofty can't read** (`audio/track/discovered.rs`), like Ogg FLAC, Matroska and WMA files: when lofty opened a file but couldn't read it, `read_file_tags` asks GStreamer's Discoverer, so the loader, the library scan, CUE sheets and covers all get them. GStreamer is asked first when lofty only took a file for MPEG or AAC audio by a frame sync in what it took for junk (`lofty_gaps::guessed_from_junk`): FLAC audio has such bytes, and without the properties, which the scan doesn't read, nothing checks the guess, so an Ogg FLAC file was read as an MP3 without tags. GStreamer parses them in C, and a file that crashed one of its plugins in the process would crash Dismas at every start, as the library is scanned at every start, until the file was moved. So each file is read in a child process: Dismas itself, started as `/proc/self/exe` (the binary running, even once another is installed over it, so the two agree) with `--discover-file`, which `main` looks for before it makes the application, as GApplication would pass the arguments on to the Dismas running. The child sets an alarm (`libc::alarm`) so that it ends even if Discoverer hangs, and writes what it found as JSON (`Discovered`); a crash, a hang or an error only leaves that file unread, which the scan stores as such. The tests, which aren't Dismas, read files in their own process. Only a file with an audio stream that a decoder can take counts, as Discoverer only parses. `utils::is_audio_type` takes `video/webm` files, whose video is never shown (`set_video_track_enabled(false)`, and the waveform's pipeline skips video decoders in `autoplug-select`, as decoding the video made it 15 times slower), and leaves out the playlists that have audio types (`.m3u`, `.pls`, `.asx`), which each cost a child process at every scan. lofty takes some WebM files for MPEG audio by a frame sync (`guessed_from_junk`), and its reading, with the wrong length, is only used when GStreamer can't read the file. Its tags become Vorbis comments, under the keys of GStreamer's own table (`gst_tag::tag::to_vorbis_tag`) and the extended comments as they are, and are read like those of an Ogg Vorbis file (`FileTags::from_comments`), through lofty's table and `lofty_gaps`, so Dismas has no table of tag names of its own; the exception is the three names ffmpeg gives Matroska tags, which GStreamer passes on as they are, `ALBUM_ARTIST`, `DISC` (split into the number and the total, as lofty only splits "1/2" while it reads a file) and `LEAD_PERFORMER` (`push_extended_comment`). The same comment is kept once, as GStreamer takes Matroska's `CONDUCTOR` for a performer. The container's tags come first: a Matroska stream's title is the name of the track, like "Audio". The bit depth is only kept for lossless codecs (`is_lossless`), as Discoverer gives the depth of the decoder's output, 32 for WMA's floats and 16 for Opus. Known limits, left until lofty reads Matroska itself (its pull request #218; `still_unread_file_types` fails when it does) and WMA (its issue #719): GStreamer's Matroska reader drops the track number and the date that ffmpeg writes. Its WMA reader (asfdemux, in gst-plugins-ugly; the decoders are gst-libav's) drops the composer, which it keeps to itself, makes the album artist a second artist, drops the genre, and only reads a track number written as a number alone ("3", not "3/24") and a year under `WM/Year`, not ffmpeg's `date`. Rhythmbox, GNOME Music and Lollypop read these tags through the same readers. Without track numbers, an album's tracks go in the order of their file names. The Flatpak's runtime has no decoder for WMA Pro and WMA Lossless, so those files aren't read there.
- **Only local files** (`audio::init_gstreamer`, which `main` and the `--discover-file` child call in place of `gst::init`): GStreamer tells what a file is by its contents, whatever its name, so a file in the music folders holding an HLS, DASH or Smooth Streaming playlist would have decodebin plug in a demuxer that fetches the streams from the servers the playlist names, at a scan, in playback and in the waveform's pipeline. Dismas plays nothing from the network, so `init_gstreamer` lowers to rank NONE the demuxers that fetch their streams: those whose class has "Adaptive", which is how GStreamer itself tells the adaptive ones, or "Network", like `sdpdemux`, in case a build gives them a rank. decodebin, decodebin3 and parsebin only plug in elements from the marginal rank up. Lowering the rank of the HTTP sources instead wouldn't do, as `gst_element_make_from_uri` ignores ranks, and `hlsdemux2` uses libsoup itself. GstPlay also plays the address that a `redirect` element message gives in place of the track, as qtdemux posts for a QuickTime reference movie, so a sync handler on the playbin's bus drops those messages before GstPlay's watch of the bus sees them (`GstBackend::setup_redirects`); Discoverer and the waveform's uridecodebin don't follow them.
- Tags and covers are read in up to four worker threads (`utils::in_threads`, `READING_THREADS`): `load_tracks()` (`audio/track/loader.rs`) sends the `TrackData` of each file over a channel, in the order of the files, all the tracks of a file at once (none, one, or a CUE sheet's), and the main thread wraps them in `Track` GObjects, which are not `Send`. The tag reader can panic on a malformed file, so every read of untrusted files (the loader, CUE claims, the library scan, thumbnails) goes through `utils::guarded`, which catches the panic and falls back; the scan stores such a file as a track without tags, in no album, so it isn't read again until it changes. Those files, and the covers, lyrics, CUE sheets and playlists that come with them, are opened with `utils::open_regular_file`, never `File::open`: opening a named pipe waits for something to write to it, which stopped the queue loader for good on a playlist that named one, and checking the path first leaves a moment in which a symbolic link can be swapped for a pipe. So the file is opened with `O_NONBLOCK`, which returns at once for a pipe, and the file opened is checked (`fstat`) before `O_NONBLOCK` is cleared; a placeholder for such a file says it couldn't be read. Lengths over 1000 hours count as unknown (`sane_duration`), as GStreamer's and MPRIS's times can't hold what a damaged header reports, and seeks are worked out in seconds with saturating arithmetic (`seek_destination`).
- **Tracks whose files are missing** (`TrackData::missing`, the `missing` property): when a playlist or the queue loads (`load_tracks` with `placeholders`), a file that gives no track becomes a placeholder named after its file (`placeholder` in `loader.rs`), which keeps its place and is saved with the others, so a playlist opened while a drive is unplugged doesn't lose its entries at the next edit. Its reason (`Missing`) is that the file isn't there, or that it is but couldn't be read (damaged, or not allowed to be opened), which its row's subtitle says; an audio file that a CUE sheet among the files splits gives its tracks there, and has none. The queue's navigation (`next_pos`, `previous_track`, `is_first_track`, `is_last_track`, `playable_from`) skips them, and so do resuming and starting over; their rows are greyed out (the `missing` class), and activating one says so. After each scan, `reload_changed_tracks` reads them again, and they become tracks once their files are back. Added, dropped and album tracks don't make placeholders.
- **A track that fails to play**: GstPlay stops on an error. `GstBackend` forwards it as `TrackFailed`, unless a load is pending, as the error then belongs to the track before it, and gives the URI of the track handed over gaplessly if that one failed; the player only follows it if it's still the next track, and otherwise goes on as at the end of the track. The player emits `track-failed` on `PlayerState` and goes on to the next track if it was playing (`after_failure`); it stops when nothing follows, when it was paused, when the next track already failed since the last one that played (`failed`, cleared by a position), so a dead queue on repeat doesn't loop, or after 3 failures in a row (`MAX_FAILURES_IN_A_ROW`), as a broken audio output fails every track and would run through the playlist. The window says so in a toast, which takes the place of the one about the track before (`failed_toast`), and greys out the track if its file is gone (`Track::mark_missing`).
- **Works** (`WorkHierarchy::labels` in `audio/track/work_hierarchy.rs`): a track is a movement when its tags name a work and a movement, and the queue and the album view show a header over the movements of each work (`work_sections.rs`). Picard's Work Hierarchy plugin writes a JSON tag, which Dismas prefers to the work and movement tags: a Vorbis comment, an APEv2 item in Monkey's Audio, WavPack and Musepack files, an ID3v2 `TXXX` frame in MP3, AIFF, WAV and AAC files, or a `----:com.apple.iTunes:` atom in MP4 files (`ExtraComments`). The plugin makes the decisions, so they're right in every player, and Dismas only shows them. It picks the work in each path (`work_index`): the top-level one, unless a part of it has a catalogue number of its own, one the works above it don't have. So each Prelude and Fugue of The Well-Tempered Clavier (BWV 846 and on) is a work, but Book I and the acts of an opera aren't, and a whole Prelude and Fugue in one track is a work of its own, not a movement. So is a whole part with a number of its own that arranges a whole work, one that's no part of another (from 0.6.2 of the plugin): each of Busoni's 10 Choral Preludes, BV B 27, which has the BWV number of the chorale it arranges, so the Works page lists it under that chorale (`a_whole_part_that_arranges_a_work_says_what_it_arranges`). Dismas names the levels below the work with the numbers their titles give them (`numeral`), and the movement with its number (`number`) unless its name has its own. A tag without `work_index`, from an older version of the plugin, leaves the work and movement to their tags. The header shows the work's own name, and Track Information its full title (`work_title`), with the collection. The movements of a work next to each other share a header (`continues_work`) when they share the work's composers (`work_composers`, from the hierarchy, or else the track's composers or artist), as a movement can credit others too: the author of the hymn in a Bach chorale, or Süßmayr in the Requiem. They must also come from the same release (`same_release`: the MusicBrainz release, or else the album and album artist), each later on the album than the one above it (`follows_on_album`, by disc and track number, or else any other track), so two recordings of a work one after the other, or a work added twice, get a header each. The header still shows the first movement's own composers, as MusicBrainz sometimes credits a work to someone else (Bach's BWV 981 to Marcello, whose concerto it arranges). When a movement is in several tracks, MusicBrainz links them all to it and marks the links "partial", so the hierarchy names them the same ("1. Ouverture" for both halves of the Royal Fireworks overture). The plugin reads the part each track has from its recording's title (`excerpt`, "Ia. Overture – Adagio"), which Dismas shows in place of the movement's name, numbered the same way; a recording's title can number a part without a dot, as in "3 Sarabande". The library keeps each track's work (`work_entry` in `library.rs`, in the `work_*` columns and `movement_order`), so that works can be found across albums. What tells a work apart is the MusicBrainz id of the work the hierarchy picks (`WorkLabels::id`); without the hierarchy's labels, the track's MUSICBRAINZ_WORKID if it performs a whole work (for a movement, that's the movement's own work); otherwise its name and its composers' keys, so that the same name and composers, ignoring case and accents, are the same work. `movement_order` is the movement's position in each level below the work (`WorkLabels::order`: the plugin's `position`, or else `number`; MOVEMENTNUMBER without the hierarchy), empty when one isn't known, and NULL for a whole work. A work the plugin (from 0.5) marks as an arrangement of another (`arrangement_of`, which it doesn't take from a link to a "catch-all for arrangements", as some originals are linked to theirs the wrong way round) is a work of its own, as the Works page goes by its id, but it often has the title of the work it arranges, so its labels have an `Arrangement`: the title of that work, and what it is, the work's disambiguation unless that's a catch-all (`is_catch_all`, as in the plugin). A track of a whole work, which `labels()` leaves to its tags, gets it from `linked_work_arrangement`, when the work the plugin picks is the one its MUSICBRAINZ_WORKID names, as the library lists it under that id; over half the arrangements of a classical library are whole works in a track, such as songs arranged for the cello. So does a track linked to an arrangement of a single movement, such as the catch-all for the arrangements of a song of a cycle, whose title the plugin splits into the work and movement tags: the library keys it by that arrangement's id (`work_entry`), as the name and composers would make it one with the recordings of the work that have no MusicBrainz ids. The library keeps them (`work_arrangement_of`, and `work_arrangement`, "" when MusicBrainz says nothing, and the id of the work it arranges, `work_arrangement_of_id`, with the ids of the parts of each track's work at every level below it, `work_part_ids`, by which the Works page lists an arrangement under the work it arranges), and the Works page and the work headers show what it is, or "arrangement", dimmed after its name (`Arrangement::shown`, which `WorkInfo` keeps too); Track Information names the work it arranges. The names of all the works in the hierarchy, their aliases (from 0.6 of the plugin: their other names on MusicBrainz, in any language, which Picard's release data lacks, so the plugin looks them up, and only searched, never shown) and the names of the collections they're in are searched (`WorkHierarchy::search_text`, added by `track_search_text`), so "Well-Tempered" finds the Preludes and Fugues, and "Trout" the "Forellenquintett"; `aliases` is null for a work the plugin didn't look up, which is why it's an `Option`, as serde would turn down the whole tag for a null `Vec`; their types aren't, as "Song" would match every song.
- **Years** (`TrackCredits::year`): the year of a track, which the library keeps for its album (the earliest of its tracks', which the grid sorts by) and for the recordings of a work, is when it was recorded, or else when it was first released (ORIGINALDATE), or else the date of the release (DATE, which Picard sets to it, and RELEASEDATE), as the date of a reissue says nothing about the recording. The recording date is a RECORDINGDATE tag, which the Work Hierarchy plugin writes from the dates MusicBrainz gives the recording's relationships, e.g. "1937-11-08/1938-03-08", and which `ExtraComments` reads like the plugin's other tag; Track Information shows it as Recorded. The library also keeps each track's first record label and catalogue number (`label`, `catalog_number`), for its album. The album's tracks show its year, label and catalogue number on a line under their header (`album_info`). The player's album line is `PlayerState`'s `album-line`, the album and the year; MPRIS and the tray keep the plain album.
- **Booklets** (`booklets.rs`): any PDF in the folder of an album's tracks is a booklet, whatever its name, as stores name them in their own ways ("booklet.pdf", "Digital Booklet - <album>.pdf", or a number), unless the folder has more than 10 (`MAX_BOOKLETS`): it's then not an album's folder but one like Downloads, which a track can be opened from, and a menu of its PDFs was as wide as their longest name, and so is one in the folder above a disc folder (`disc_album_folder`), as for the covers (`CoverCache::cover_files_for`); a CUE sheet's tracks look next to the sheet. `booklets::find` reads the folders, so it runs in GLib's pool, as the menus open: the album's (for an album on its own, not a selection, from `library::album_tracks`) and the track's (`Window::add_booklet_item`, which adds the item once they're found, and nothing without one), the player's More menu (its `booklet_section`, filled in at each change of track, `update_playing_booklets`), and the album pane, which looks with the album's tracks and shows a button for one booklet and a menu button for several (`show_booklets`). With several, the item is a submenu of their names (`booklets::labels`): without the extension, and shortened to 40 characters when they're longer, as a popover menu is as wide as its widest page, submenus included. A long name keeps its start and its end, where the booklets of an album often differ ("CD 2"), cut between words; names that would then be the same show the part where they differ instead, and those still the same are left whole. They open through `win.open-booklet`, with the booklet's URI as its target, installed on the class so that other programs can't open files with it over D-Bus. Outside Flatpak (`utils::in_flatpak`), they open in the default app for PDF files (`gio::AppInfo::launch_default_for_uri_future`, from mimeapps.list) rather than through `gtk::FileLauncher`, which goes through the desktop portal wherever one runs: its OpenURI asks which app to use while several can open the file, until it has remembered a choice for the app's ID, and on a session without systemd it has none for an app outside a sandbox, so it asked every time. In Flatpak, the launcher hands the file to the portal, like Open Directory.
- **Discs** (`library::Disc`): the disc of an album a track is on is its number in the tags, or else the disc folder it's in (`is_disc_folder`), by which `TrackOrder` orders the tracks without a number, and with neither the first; `Track::disc` takes the folder of the audio file, which a CUE sheet is next to. The album pane, for an album on more than one disc (`library::album_tracks_and_discs`, read with its tracks, before they're shown, as their headers read it), starts a section with each disc (`shares_section`, the queue's rule, and the same disc), and the work header's `disc_line` names it above the work: "Disc 2", with the disc subtitle, or the folder's name. So a work that goes on to the next disc is named again under it. The queue mixes albums, so its headers name no discs.
- **Performers**: the library keeps, in its `performers` column (`performer_entries`), the conductors and performers that a track's credits line names (`TrackCredits::listed_performers`), each with its kind (conductor, ensemble or soloist, `PerformerKind`), key (`composer_key`), name, sort name (the last name first for people, `sort_name`, and the name itself for groups) and role. Picard lists every player of a group with it, so, as in the credits line, only the soloists and the groups are listed when there's a group, and when more than five players have none, the names in the album artist (`ensemble_in_album_artist`): the ones the tags credit are the players they say, and each of the others is taken to be a group, as joining the names next to each other made one ensemble of two singers. The Performers button, next to Composers, lists them (`library::performers`), set up by the same `setup_picker` as the list of composers, so with a composer picked or words searched for it has only the performers of the tracks they match, with the number of those albums (on the Works page, only the tracks of works count, and the number is of works, `library::Counted`, so that picking one never shows no works): each performer once, by key, as the kind most of their albums give them (all their albums, whatever the filter, so that a performer stays under the same header, with the same names and roles; conducting first, then playing, when they're as many; a name only guessed from an album artist, an ensemble without a role, counts only when nothing else does, as it can be a singer the tags of other tracks credit), under the headers Conductors, Ensembles and Soloists (a section sorter on the kind; All Performers is in a section of its own, whose header is empty), with their roles after the name, dimmed, the most common first, which its search looks into too, so "piano" finds the pianists. Picking one filters by its key whatever the kind (`TrackFilter::performer`, which looks for `\t{key}\t`), so a conductor's albums include those they play on. It combines with the composer and with the words; the page's subtitle names both, once if they're the same person, the bar over an album's tracks says how many are theirs without words or the heart, and Esc in an empty search clears both (`clear_picks`). The button is hidden while no track has a performer (`library::has_performers`).
- **CUE sheets** (`cue_sheet.rs`) split an audio file into tracks: a `.cue` file next to it, or a `CUESHEET` tag (a Vorbis comment, or an APEv2 item for Monkey's Audio, WavPack and Musepack, which `read_tagged_file` reads into `ExtraComments`). A track of a sheet is at a path under the sheet, `Album.cue/track03` (or `Album.flac/track03` for an embedded sheet), which can't be a file, so the queue, playlists, resume points, unshuffled orders and the library keep it like a file's path; `Track::audio_file()` is the file that plays, and `Track::segment()` the part of it. A sheet only splits the files it has two or more tracks in (multi-file rips keep their own tags). The sheet that splits a file is the same however the file was reached: in a list of files, the first `.cue` that splits it (`Claims`), otherwise the first in its folder, otherwise the embedded one. Its tags are the audio file's, minus the ones about the whole file (`FILE_ITEMS`, such as its title, ISRC and lyrics), with the sheet's over them (`album_tag`, `track_tag`), so all the code that reads lofty tags works on them. Every track of a sheet keeps a copy of those tags, so a crafted file with a large tag and hundreds of tracks could fill the memory: all the tracks of a sheet together keep at most 16 MiB of the file's items (`MAX_SHEET_TAG_TEXT`, divided by the number of tracks), and `album_items` keeps the smallest items first, so that a long comment is the one left out rather than the artist and the album, and counts the size of each item as well as its text, so that a million empty items count too. Each value of a sheet is cut at 1 KiB (`MAX_SHEET_VALUE`), as CD-Text allows 80 characters and an embedded sheet has no size limit, except the file names, which the sheet keeps once rather than for each track. A name the sheet replaces with another loses the file's sort names for it (`set_name`), as they'd be the other name's: a track whose SONGWRITER isn't the composer the file names would sort under that composer. Sheets in legacy encodings are guessed with chardetng. `load_tracks` reads each sheet and each split file once for all their tracks (`FileCache`). Exported playlists name the tracks the same way, which only Dismas reads. In Flatpak, a `.cue` opened through the document portal from outside the Music folder can't reach its audio file. FLAC's binary CUESHEET block isn't read, only the tag.
- **Playing a part of a file** (`gst_backend.rs`): positions and seeks are relative to the track. A track that doesn't start at 0 only plays once GstPlay says its file is loaded (`TrackLoaded`), as GstPlay drops a seek made before it loads a file; seeks are accurate. When the next track goes on from the end of the current one in the same file, the pipeline plays on, and once the position is past the end the backend sends `TrackAdvanced` (the player confirms it like a hand-over). Otherwise a probe on the audio filter (always set: an identity without ReplayGain) clips the audio at the end and pushes an EOS, so the sink plays the rest and the usual `PlayNext` follows. Only after a track that plays to the end of its file is the next one handed over, and only if it starts at 0. The stream's ReplayGain tags are about the whole file, so a second probe, before rgvolume, sends it the track's gains (from the sheet, or else the file's; for a whole Opus file whose tags only have R128 gains, which GStreamer doesn't pass on, those, turned into ReplayGain gains, `ReplayGain::r128`: 1/256 dB, and 5 dB more, as they're to −23 LUFS rather than −18) as a tag event before the first buffer of each track that reaches the filter, which runs about 2 s ahead of the sink; a tag event only replaces the gains it has. With the automatic ReplayGain, the same probe sets rgvolume's `album-mode` there, from the track's `album_order` (`Gapless::auto_gain`), as the hand-over comes too early and `TrackAdvanced` about 2 s late. `rgvolume`'s `result-gain` is the gain of the audio passing it, not of what's heard.
- **Pausing a track that hasn't played** (`GstBackend::pause`): with PulseAudio, a pipeline prerolled to PAUSED that only starts playing a few seconds later plays, but its position stays where it started. GstPlay then reports no positions, so the time, the waveform and the play stats stand still while the album goes on gaplessly, and pausing or seeking it afterwards can stop the sound for good. A track that has played since it was loaded (`Gapless::played`, set when GstPlay says it's playing) pauses and seeks safely, whatever the wait. So a track that hasn't played is never paused in GStreamer. One that wasn't asked to play (a resumed track, or one loaded while paused, which a Pause from MPRIS or the tray still reaches) stays unloaded. One that was asked to play but hasn't started yet, as with a quick Play and Pause, is loaded again. Either way, it starts where it would have (`starting_at`) once it plays.
- `WaveformGenerator` builds the seek-bar waveform in a separate GStreamer pipeline; for a part of a file, it seeks to it once the pipeline is ready. While `show-waveform` is off, it neither reads the cache nor runs the pipeline. The cached peaks are a small binary format (`encode_peaks`: a versioned header, then two little-endian u16s per quarter second); a JSON file from older versions is converted when it's loaded. At startup, `audio::remove_old_cache_files` removes the cached waveforms and MPRIS covers not used for 90 days; using one touches its mtime.

### UI

- **Composite templates:** each widget is a Rust subclass (`src/*.rs`) bound to a Blueprint template in `src/gtk/*.blp`.
- **Resources:** Meson compiles the `.blp` files to `.ui` and bundles them with CSS and icons through `src/dismas.gresource.xml`. Templates load from `/io/github/dachshund7/Dismas/<name>.ui`.
- **Adding a widget:** update the `.blp` list in `src/gtk/meson.build`, the gresource XML and `po/POTFILES.in` together.
- **Scrolling a list with headers to its top** goes through `utils::scroll_to_top_when_laid_out` (the works, an album's tracks as they're read, the queue after a sort): once its items change, GTK shows the first one at the top, with its header above it out of view, and setting the top in the same frame does nothing, or makes a long list jump to its end (GTK 4.22), so it's set at the next frame, once the list is laid out, as long as it's still wanted (not once a track to reveal was scrolled to). While the heights of the rows it hadn't measured settle, in the frames after, GTK can put the first item back at the top, below its header, as after sorting a long queue, where it first follows the item it kept its place by to its new place; so the top is set again at each frame until it stays there for two frames in a row, for at most 10 frames (`TOP_FRAMES`).
- **Tooltips that change often** are made when they show, in `query-tooltip`, rather than set: the rows of lists and the cells of the grid (`utils::set_row_tooltip`, `QueueRow`, `AlbumCell`), never as they're bound, and the sleep timer's, which says the time left. On X11, setting a tooltip makes GTK look for the window under the pointer, which grabs the X server, and lists bind many rows a frame while they scroll, which stalls the whole display. An X server that does nothing else, like Xvfb, hardly shows the cost.
- **Track rows** (`QueueRow`, in the queue and an album's tracks): each line, the title and the one or two under it, wraps to two lines and then ends in "…", as the pane can be under 250 pixels wide beside the player. They're `Label`s, as an `Inscription`'s height doesn't follow its text, so only the rows with long text are taller. A label measures its text as its row is bound: with 1,500 tracks in Xvfb, scrolling the queue took about 7% more CPU, and Pango and HarfBuzz went from 8% to 19% of it. The icon of the track playing, or paused, is over its cover, on a scrim, so no row keeps room for it at its end. The copy of a dragged row is clamped to the row's width (`adw::Clamp`), as a label's natural width is its whole text on one line, and that width is the row's bounds (`compute_bounds`), as `width()` leaves out the padding that a size request includes.
- **Stale resources after editing `.blp` files:** the gresource bundle doesn't track the compiled `.ui` files, so the first `ninja` run can leave the old UI in `_build/src/dismas.gresource`. Run `ninja` a second time.
- **Window coordination:** `Window` is the coordinator. `window.rs` holds its template, properties and `win.*` actions, and its methods are split by area into `window/*.rs`: `adding.rs` (Play Next, and adding tracks to any playlist), `bindings.rs` (binding `PlayerState` and the queue to the widgets), `booklets.rs` (opening the booklets of albums), `favorites.rs` (the heart button, and marking tracks from their menu), `find.rs` (where Ctrl+F and typing go, see Keyboard shortcuts), `loading.rs` (opening files, drag-and-drop, restoring the queue), `playlist.rs` (the playlist pane, which shows the queue), `selected_playlist.rs` (selecting, saving, creating, renaming and deleting playlists), `selection.rs`, `albums.rs` (the album grid), `now_playing.rs`, `pane.rs` (the pages of the playlist pane, see Lyrics), `sidebar.rs`, `sleep_timer.rs` (the sleep timer popover; the countdown itself is `audio/sleep_timer.rs`), `smart_playlists.rs`, `track_menu.rs` and `zen.rs`.
- **Keyboard shortcuts:** GTK runs the application's accels (`set_accels_for_action` in `application.rs`) before the focused widget sees the key, so a key that a focused widget can use too isn't an accel. Ctrl+A is a shortcut in the window's capture phase, which leaves it to a search with text it can still select (`setup_select_all_shortcut`). Space, Home, End, Page Up, Page Down, Ctrl+Left and Ctrl+Right go through a capture-phase handler that leaves them to text entries where they edit the text (`setup_key_shortcuts`), and Home, End, Page Up and Page Down to a focused slider or the waveform. The waveform seeks with the arrows as they're pressed, so a held key repeats, and with Home and End; it's drawn from the right in right-to-left text, so the arrows go the other way there, and it has the theme's focus ring (`style.css`), as it draws none itself. Ctrl+C is a shortcut in the window's bubble phase (`setup_edit_shortcuts`), so text with a selection copies it first; text without one turns its copy action off, and the key comes on to the window, which copies the details of the track whose row has the focus (`copy_focused_track`, through `utils::focused_child`), or else of the playing track. The More menu's Copy (`win.copy`) is the playing track's, as the menu is about it, and the track menu has a Copy of its own. A dialog keeps its keys from the window's controllers, the accels included, as libadwaita sets its `limit-events`, as for a modal window, so in a dialog Ctrl+W is a shortcut of the dialog that shows (one controller, moved to it at each `visible-dialog` change), which closes it as Esc does. Ctrl+Z presses the button of the toast with an Undo, while it's up (`add_undo_toast`, which keeps it in `undo_toast` and dismisses the one before, as a toast waits behind the one showing, which would name an older change than the one Ctrl+Z undoes; `press_undo` dismisses it, as emitting `button-clicked` doesn't), with a shortcut in the capture phase, as GTK's text takes the key even with nothing to undo; a search with text keeps it, to undo its typing first. The Menu key and Shift+F10 open the menu of the focused track or album, as a right click does (`utils::setup_menu_key`, on the queue, the album's tracks, the grid and the covers of an open work): the focus is on the list's item, or the flow box's, so the shortcut is on the list, which finds the row or the cell in the item (`utils::focused_child`). Alt+Up and Alt+Down move the queue's focused track, or the selected tracks with it, a place up or down (`setup_move_keys` in `window/playlist.rs`), through `move_queue_track`, as a drop would, so the rows slide and the focus stays on the track; not while the search filters, as with dragging. Ctrl+F (`win.find`) and typing go to the search of where the focus is (`focused_search` in `window/find.rs`): the album search on the album pages, unless the focus is in the playlist pane, and the queue's otherwise, as the player and the playlists have none. Ctrl+F selects the search's text, as a browser's find bar does, so that typing starts a new search (a `gtk::SearchEntry` takes the focus without selecting), while typing elsewhere goes on with it. Typing goes through a key controller in the window's bubble phase, for keys that no text entry took, from the content only, not a popover or a dialog. GTK runs a widget's controllers added last first, so it comes before the window's bindings, and only takes the keys that type (`types_text`: a character, Backspace, or a dead key or Compose), leaving Delete and Esc to them: it forwards the key to the search's text, and moves the focus there once the text changes, as a dead key only starts a letter. The queue's search opens with it while the pane shows the queue. GTK's own capture, which it replaces, left the focus where it was, and went nowhere once the search was open. The glide to a track that was asked for (`queue_row::flash_track`: Show the Playing Track, Show in Playlist, Go to Album) ends with its row taking the focus (`arrive`); following the playing track (`reveal_track`) leaves the focus where it is. **Lost focus:** when the focus is lost rather than moved, as when a menu's action takes away the row or the album it was opened on (the last favorite unmarked while the heart shows only favorites), GTK keeps the chain of focus children that led to it, and a list item whose focus child can't take the focus refuses it, so the keys skip the list, or stop at it without moving the focus. `popup_menu` drops those links above the row or the cell once the menu is gone (`utils::forget_focus_above`), and the album view drops the ones of its stack and of each page that don't lead to the window's focus each time that changes (`LibraryView::setup_lost_focus`, `utils::forget_focus_below`); GTK's lists then focus the item they last focused when the keys come in.

- **The queue's search** (`SearchFilter` in `search.rs`) only filters the pane. Playing a track it found plays it at its place, and Next and the end of a track go through all the tracks, so playback never depends on a search left open in a hidden pane. Its play button (`queue.play-results`) plays the tracks found in place of the queue, with the Undo of `play_in_place_of_queue`. Its text is a query of the search syntax (see The search syntax), matched by `Track::matches_query` with a `Context` taken as the text changes, the favorites' URIs read only for a query with `is:favorite` and again when one is marked (`favorites_changed`, from `Window::mark_favorite`), and the path only for `path:` (`TrackData::search_path`: the one shown, or a CUE track's under its sheet). While it filters (`filtering`: the query doesn't match every track, as an empty one, or `sort:x` alone, does), the rows aren't reorderable, as two rows next to each other can be far apart in the playlist, so tracks dropped on the pane go to the end. Adding tracks (except with `QueueMode::Quiet`) and switching playlists (`replace_selected_playlist`) close it (`close_queue_search`), as the tracks that came in rarely match it, and Show in Playlist, in a result's menu, closes it and flashes the track. A query with an error matches nothing (`FilterMatch::None`). `search::setup_query_entry` shows what's wrong with a search, for the album search too: on `search-changed`, the entry gets the `error` class and the Invalid state while the query has an error; the error, or else a hint (a near field name, directives in a search), shows in a line under the entry (`queue_search_problem`, a `Gtk.Revealer` in the search bar, with a Search Syntax button; on the album pages, `search_problem`, an `Adw.Banner` under the search bar, whose title isn't markup, as the syntax has "<") half a second after the text stops changing (`PROBLEM_DELAY`), so that it doesn't come and go with each key, and closes at once once it's fixed; it's announced once (`announce()`, as a change of description isn't said), and is added to the entry's description; the tooltip, made in `query-tooltip`, says what can be typed. **Search Syntax** (`search_syntax.rs`, `win.search-syntax`, in the main menu and on the problem lines) is an `Adw.Dialog` of groups of rows, the syntax as the title and what it does as the subtitle, made from `Field::ALL` and `IsFlag::ALL` with their `description()`, so it lists every field and only those.
- **The album grid's search** finds albums by their tracks, matched like the queue's, by the same evaluator (`Query::matches`). The library runs it in SQL as `dismas_match(matcher, search, fields, path)`, a function every connection gets in `open_at()` (`add_functions`, which also adds `dismas_length(fields)`, a track's length from its `ln` line, for Play a Random Work; rusqlite's `functions` and `pointer` features). Each statement binds its own search as a pointer, an `Rc<Matcher>` (the query, the `Context` taken when the statement's values are made, the favorites' paths and the portal folders' paths outside the sandbox, from `SearchSources`), through `Param`, the values of `TrackFilter::conditions()`, which puts it last so that SQLite checks the cheaper conditions first, and passes NULL for the columns the query doesn't need (`Query::needs`). So a statement can't match with another's search, and one without its search fails. `TrackFilter::query` parses the entry's text (`None` when it matches every track), and the filter is `Eq` over the query, the picks and the heart only. 50,000 tracks took 25 ms with plain words, against 27 ms with `instr()`, and 34 ms with fields (`time_library_searches`). The grid is on two pages, Albums and Tracks (`LibraryPage`, which share it, with its sort, place and selection), which differ in what's taken from an album, through one method, `LibraryView::taken`: on Albums, adding, playing, dragging and opening an album take all its tracks; on Tracks, only those that match (the `library::TrackFilter` of the search's words and the composer and performer picked, which `album_files` filters by), and the cover of an album matched only partly counts them (`update_match_counts`, zeros on Albums), and while albums are selected during a search, the selection bar says how many tracks the buttons take. An album opened from Tracks gets the filter, and lists only the tracks it matches, under a bar (`filter_bar`) that says how many of the album's tracks those are (`AlbumTracks`'s `matching`), or with only the heart on, how many are favorites; the Play and Add buttons take them (`files`), and a click on one plays them from it (`files_to_play`). The pane keeps the tracks it opened with: a new search, or a track unmarked as a favorite while it shows, changes them once the album is opened again. The Albums page opens the whole album. The entry takes Esc, which clears the search, and in an empty search does what it does elsewhere in the window (`Window::escape`). The heart after the Composers and Performers buttons (`favorites_button`, `setup_favorites_filter`) shows only the favorites of the page: on Albums, the favorite albums, through the filter (`TrackFilter::favorites`, `Favorites::Albums`, the ids as `album_id IN (…)`, nothing for none); on Tracks, the albums with favorite tracks, taking only those (`Favorites::Tracks`, their paths as `path IN (…)`), which `favorite_tracks` reads on the main thread the first time the heart needs them, and keeps until `favorite_tracks_changed`, which `Window::mark_favorite` calls for the track menu and the player's heart alike. Each is added by `wanted_filter` on its page only (`heart_filters`), so that switching pages while it's on searches again (`update_album_matches`), and the pickers' lists follow it there; on Works, the favorite works, which `update_works` keeps from those read, so the pickers list the people of all the works there. It's one button for the pages, named by its tooltip ("Show Only Favorite Albums", "… Tracks" or "… Works", `update_view`), filled and highlighted while it's on; Esc in an empty search turns it off with the composer and performer (`has_picks`, `clear_picks`), and so does going to an album or a work it hides (`clear_search`; `reveal_album` asks the heart too, as the albums it shows can still be read when the album is gone to from another page). While it finds nothing, the page says so (`finds_no_favorites`, the stack's `no-favorites` page, only once the matches read are for the page's own filter, as just after the Albums and Tracks pages switch they're still the other page's): how to mark favorites, or that none matches the rest of the search. That page has nothing to focus, so the focus goes to the search when it was on the page that goes, or nowhere (`update_stack`). Hiding the pane on the album page puts the cursor in the search (`set_playlist_visible`), as the split view would move the focus to the first widget of the page beside the pane, or back to where it was before the pane covered the page, and a click leaves it on a button or an album; Down goes back to the album that had it.

- **Zoom** (`zoom.rs`, `window/zoom.rs`): Ctrl+plus (and Ctrl+=, and the keypad's), Ctrl+minus and Ctrl+0, the HIG's Zoom In, Zoom Out and Normal Size (and Ctrl+_ and Ctrl+), which a US keyboard types with Shift still held from Ctrl+plus; GTK matches an accel by the character typed, so `<primary><shift>0` never matches), go through `win.zoom-in`, `win.zoom-out` and `win.zoom-reset`, which zoom what the focus is on (`zoom_target`), as Ctrl+F searches there: the covers on the album pages, unless the focus is in the playlist pane or the pane covers the page, and the lyrics in the pane, or beside the player and the playlists, which have nothing to zoom. The bell rings at an end, or with nothing to zoom. Ctrl and the mouse wheel zoom what's under the pointer: a capture-phase `EventControllerScroll` stops each scroll with Ctrl held, so that the view doesn't scroll too, and `ScrollSteps` adds up a high-resolution wheel's fractions of a notch, and a touchpad's pixels, into steps. A pinch on a touchscreen or a touchpad zooms the same way (`zoom::add_pinch`): a `GestureZoom` in the capture phase, which claims the fingers as it begins, cancelling the scrolling and the long press the first finger started, and steps each time they move a quarter farther apart or closer (`PinchSteps`); it's untested, as there's no touchscreen here. The covers' step is the `cover-zoom` setting (−2 to 1), which the cells of the grid and of the works bind to (`LibraryView`'s `cover-zoom`, `AlbumCell`'s `zoom`, `SquareBin::set_size_range`), each with a table of the sizes its cover grows between at each step (`COVER_SIZES`: 90–120, 120–160, 160–240 and 240–320 pixels; `WORK_COVER_SIZES`). GridView counts its columns by the covers' smallest size and stretches them to fill the row, so each step starts where the one before ends: with sizes that overlapped, as 0.8 and 1 times the normal ones did, a grid of three or four columns could keep its columns, and its covers' size. The grid's `max-columns` grows as they shrink, so that the grid is never wider than six columns of the normal size (`max_columns`), and so does the cache of covers (`cache_capacity`, about as many pixels at any step). The `library.zoom-*` actions zoom the covers whatever has the focus; zooming in and out are off at their ends, but not the size between them, which would grey out the size it shows. They're the buttons of a `ZoomRow` (− 100% +, as in Text Editor's menu) at the top of the album pages' main menu (`setup_primary_menu_button` puts it in a section of its own, a `custom` item, as setting another menu model would replace the popover and lose its F10 controller); the lyrics have one in a menu button of their header, Text Size. The lyrics' step is `lyrics-zoom` (−1 to 3: 85, 100, 125, 150 and 200 percent, `ZOOM_PERCENTS`), a `zoom-{percent}` class on the `LyricsView` that sets the `font-size` of its text view and list in `style.css`, and its `lyrics.zoom-*` actions are those of the lyrics. Its Ctrl+wheel controller is on the view itself, an ancestor of the scrolled window of the lines, so that it comes before the one that leaves the lines where the user scrolls them; a zoom puts the line sung back in the middle once the rows are laid out again (`center_when_laid_out`), and keeps the line at the top of plain lyrics there with a text mark.
- **Settings:** stored through GSettings (`data/io.github.dachshund7.Dismas.gschema.xml`). The main menu only has actions; the settings are in the Preferences dialog (`preferences_dialog.rs`, Ctrl+,), whose switches are bound to their keys, so what depends on a setting watches it or reads it when needed. Its ReplayGain rows go through `win.replaygain`, the window's `replaygain-mode`, which passes the mode on to the player. Automatic (`ReplayGainMode::Auto`, stored as 3, after the older modes) takes the album gain for a track that plays as part of its album (`plays_in_album_order`: the track before or after it in the queue continues its album, `Track::continues_album`, the same release later on the album), which the player gives the backend as the `album_order` of the track's `TrackSource` (`source_of`), and the track gain otherwise; the gain probe switches rgvolume to it (see Playing a part of a file), and a change of the mode applies to the track playing at once. `replaygain-preamp` (Pre-amp, an `Adw.SpinRow` bound to it, off while ReplayGain is) is rgvolume's `pre-amp`, which the player watches (`setup_preamp`); rgvolume adds it to the fallback gain of tracks without gains too, so those move as much, and limits a gain by the track's peak, which it takes to be full scale without one, so it never raises those. `move-from-header-bars`: header bars move the window by default, like other GTK apps (on Wayland it's the only way), and turning it off turns off their drag gestures (`utils::set_window_drag`), right away, for window managers that move windows themselves. Empty areas of the content never move the window. `volume` is saved by the player within half a second of the backend reporting a change, as dragging the slider changes it many times, and at shutdown; it's applied at startup, so the slider is right before anything plays (PulseAudio only restores an app's volume when its stream opens, and keeps one it's given); until it has been saved once, PulseAudio's volume stays. `repeat-mode` is saved whenever the queue's mode changes (from the button, its shortcut Ctrl+T, as Ctrl+S shuffles and Ctrl+R scans, or MPRIS) and applied at startup. The window's size is saved by `Window::save_window_state`, when the window is closed and in `Application::shutdown`, as quitting doesn't close it. `playlist-visible` is the user's own choice: the pane button, F9, the back button and Esc go through the window's `user-playlist-visible` (the `queue.toggle` action), which stores it, except in the collapsed split view, where the pane only covers the player for a while. The pane opening or closing by itself (added tracks, drops, search, Show the Playing Track, an empty queue) goes through `playlist-visible` and isn't stored. At startup, neither restoring the queue nor the files Dismas is opened with open the pane: opening it as the window first showed made the window wider by the pane, which it kept (the split view's layout, in its first frames, asked for the whole window and the pane beside it). `show-waveform` (Show Waveform in Preferences) swaps the `WaveformView` for a stock `Gtk.Scale` (`seek_scale`), bound to the setting's visibility; both seek through `Window::seek_to`. `zen-mode` (Zen Mode): with the playlist pane hidden on the player page, `window/zen.rs` waits 3 s once the pointer leaves the window, focused or not (with focus following the pointer, the window keeps the focus when the pointer goes to an empty part of the screen), then fades out the header bar and the `PlayerBox` children with the `player-controls` class, while `PlayerBox::set_zen_progress` blends the player from its layout with the controls (`shown_layout`) to one without them (`zen_layout`): the cover and the track details move to the middle of the toolbar view, under the faded header bar, and the cover grows into the room that the controls and the header bar leave, as far as the width allows. `TrackCover` draws the square it's given, from the medium size up, so it grows smoothly. Only the allocation changes, not the measured sizes, so the window's size limits stay put. The controls are drawn under the cover and the details as they fade. They fade out over 600 ms (ease-in-out) and back in over 300 ms (CSS's `ease`, quick without jumping), as the cover shrinks back. The pointer entering or the window getting the focus (`is-active`) fades the controls in again, for 3 s if the pointer is elsewhere. Whether the pointer is over the window is asked for (`pointer_widget`) rather than taken from `contains-pointer`: when a drag is let go outside the window, GTK puts the pointer back over the window and no leave follows, so moving over the window brings the controls back too. Each step of a resize starts the wait again, as dragging an edge has the pointer outside the window. On touchscreens, a tap (a touch-only `GestureClick`) brings the controls back and starts the wait again. So does a key press (an `EventControllerKey` in the capture phase, before the window's handler of Space and Home, which stops them), so that Tab doesn't go through buttons that can't be seen; the accels' keys, like Ctrl+Up, don't, as GTK stops them before any controller added after its own. Faded out, the controls and the header bar don't take input (`can-target`), so a tap can't press a button that can't be seen.
- **Lyrics** (`lyrics.rs`, `lyrics_view.rs`, `window/pane.rs`): Lyrics, in the player's More menu, and Ctrl+Shift+L (`win.lyrics`, a property action on the window's `lyrics-shown`; Ctrl+L is Remove All) show the playing track's lyrics as the third page of the playlist pane, as Apple Music shows them in its sidebar. `lyrics::find` takes the first synchronized lyrics among the files of lyrics next to the audio file with the same name (`lyrics_file_paths`: an LRC file, then a text file, which can be in the LRC format too, each with its extension in capitals if there's none in lowercase; decoded like CUE sheets), an ID3v2 SYLT frame, and the Lyrics or UnsyncLyrics item of its tags (Vorbis LYRICS and UNSYNCEDLYRICS, ID3v2 USLT, MP4 ©lyr, APE Lyrics, and the LYRICS of the GStreamer fallback, which never gives SYLT), or else the first plain ones. A file of lyrics over 1 MiB isn't read, nor one that isn't a regular file (`utils::open_regular_file`), and neither are lyrics in the tags over 1 MiB. A text is synchronized when at least as many of its lines of text have a time as don't (`parse`): a line with several times is one for each, `[offset:±ms]` moves them all (a positive one earlier), header lines like `[ar:…]` are skipped and the times of words (`<mm:ss.xx>`) taken out, lines at the same time are one (a line and its translation), a line without a time right after one with a time goes on from it, and a timed empty line ends the line before it (`Line::end`); otherwise it's plain, without the times (`text_without_times`). A line is copied once for each of its times, and a line without a time once for each time of the line it goes on from, so lyrics whose copies would come to more than 4 MiB (`MAX_SYNCED_TEXT`) aren't synchronized lyrics, and are taken as plain; a crafted line of 100,000 times made 50 GB of copies. The closing bracket of a time is only looked for within the 12 bytes that the longest time takes (`MAX_TIMESTAMP_LEN`), so taking the times out of a line of many "<" takes no longer than the line's length. SYLT frames are only read when asked (`ReadOptions::LYRICS`, into `ExtraComments::synced_lyrics`), so the scan never parses them; the ones with times in milliseconds, those of lyrics or a transcription first, whose entries are lines, or words when some of them start with a line break, which then start the lines (`sylt_lyrics`). A track of a CUE sheet (`Track::part`) gets the synchronized lines sung in its part of the file, from its start, and no plain lyrics, which are the whole file's (`in_part`). They're only read while the view is mapped: on map, when the playing track changes, when its tags are read again (`show_updated_track`), and when one of its files of lyrics is written or removed (a `gio::FileMonitor` on each path, as a lyrics downloader writes them while the track plays, and the audio file doesn't change, so the scan doesn't read the track again). `Track::update` changes a track in place, so two reads of one track can't be told apart by the track: each read takes a number (`reads`), and only the lyrics of the last one show. A read of the same track keeps what shows, and its place, until the new lyrics are there, and the same lyrics keep their rows. Plain lyrics are a read-only `GtkTextView`, so that they can be selected and copied, and read with a caret by screen readers; while it has the focus, it keeps Home, End, Ctrl+Left, Ctrl+Right, Page Up, Page Down and Ctrl+A (`setup_key_shortcuts`, `select_all`), and Space still plays and pauses. Synchronized lyrics are a `GtkListBox`, a row for each line, named by its text (a row has no name of its own), so that every line reaches screen readers and the arrows go from line to line; the line sung has the `current` class (the accent color, with the others dimmed, which leaves the rows' height alone) and the description "Current line", and nothing is announced as lines change. The view follows the position while it's mapped: `PlayerState::position_time()` at each position (about four times a second), and a timeout for when the line changes next while playing (`lyrics::next_change`), so that each line shows at its time; a position up to 300 ms before the line that shows keeps it (`BACK_TOLERANCE`), as one reported after the timeout can be from a little before it. The line sung glides to the middle (an `adw::TimedAnimation` of the adjustment, with the queue's `GLIDE_DURATION` and easing), and is centered at once when the list's size changes and two frames after new lines. Scrolling them leaves them for 4 s (`FOLLOW_PAUSE`), told from what the user does rather than from the adjustment, whose value changes with new lines too: the wheel and the touchpad's scrolling (an `EventControllerScroll` in the capture phase, with its deceleration), a finger (a touch-only `GestureDrag` that never claims), the scrollbar, `scroll-child` (Page Up and the like, which the window gives the list) and the list's `move-cursor`. Tab into the lines puts the focus on the line sung when the focus shows (`focus_current_line`), and a line activated (Enter, a click, a tap) plays from its start (the view's `seek` signal, `seek_position_abs` and `play`). The view takes Enter on a line itself, as the list left it to the window, where it pressed the play button, the default widget. The item and the accel are off without a track and in fullscreen (`update_lyrics_action`), and the menu item is hidden then. The pages of the pane (`window/pane.rs`): an album's tracks and the lyrics open over the page that shows (`open_pane_page`), and going back (the back buttons, a swipe to the right, turning the lyrics off) shows it again: `PaneHistory` keeps the pages under the one that shows, and whether the pane was open under the queue, so that going back to the queue closes the pane if it was opened for the page. Showing the queue itself (`show_playlist_view`, e.g. when tracks are added, or with Ctrl+F) empties it. Esc and F9 hide the pane on the lyrics as on an album's tracks, and F9 or the item shows them again. When the queue empties, the pane leaves the lyrics for the queue (`reset_queue`). The lyrics' property getter checks that the stack is bound, as GTK reads the states of the window's property actions while its template is built.
- **Fullscreen** (F11, `win.fullscreen`, a property action on GtkWindow's `fullscreened`, and Fullscreen in the main menu, `win.enter-fullscreen`, which a touchscreen without a keyboard needs; the menu would show the property action with a check box, and its button is hidden in fullscreen): everything follows that property, so the window manager's fullscreen does the same (`window/fullscreen.rs`). It goes to the player and hides the pane without storing it, and leaving goes back to the page and the pane from before; the collapsed split view doesn't show the pane again in fullscreen, and leaving hands the pane to `sidebar_visible_uncollapsed` if the window is collapsed by then, as the window and the breakpoint can change in either order. The backdrop is the shared cover, blurred small once per cover in another thread (`CoverImage::backdrop`) and scaled up, rather than a blur node, which the renderer could blur again over the whole screen whenever the waveform redraws. - **Match Cover Art** (`enable-recoloring`): `update_style` (`window/now_playing.rs`) writes the cover's palette as `--background-color-N` on `:root`, and the stylesheet makes tints of them in OKLCH, keeping their hue and a little of their chroma at a lightness set by the color scheme, so the text keeps the theme's contrast. To tune it on real covers, the ignored test `print_palettes` (`audio/cover_cache.rs`) prints the palettes of a music folder. - **The library** keeps a row per track, with the file it comes from (`file`: the track's own, or the `.cue` or image of a sheet); the scan compares the time and size of each file (a `.cue`'s include its audio files'), and reads a changed file's tracks again together, the changed files a few at a time (`utils::in_threads`), 200 to a transaction, which is written on the scan's thread as they come: a first scan of 2,104 small tracks took 125 ms rather than 309 (`time_scan`). Each track keeps when it was added (`added`): when the scan first found its file, by the file's birth time, or its modification time without one, kept when the file changes. A schema bump drops the tracks, but `keep_added_times` copies those times into `added_times` first, which the scan takes for the files it reads again and then empties, keeping only those of the folders that aren't there; otherwise every track would count as added at that scan where there are no birth times, or where a sync tool replaced the files. The album grid's covers are thumbnails the scan makes in `~/.cache/dismas/album-covers`, as large as the grid shows them on the monitor with the largest scale (`thumbnail_sizes` in `library_view.rs`: 240 pixels, or 480 from a scale of 2, and 320 or 640 with the covers zoomed in, see Zoom; zoomed out, they're kept at the normal size and scaled down as they're read), and as JPEG, which takes a fraction of the room and of the time to read that PNG does, unless the cover has transparency; their names have the size and the format (`{id}-{size}.jpg`, or `{id}-{size}-alpha.png`), so a thumbnail smaller than that size, or in another format, like the PNG files of older versions, is made again, and `remove_unused_covers` deletes the old one (`ThumbnailSizes::update`). A larger one made for a monitor at a scale of 2 is kept, as the monitors connected can change from one start to the next, and docking a laptop would otherwise make every thumbnail again; any other larger one was made while the covers were zoomed in, and is made smaller from itself (`shrink_thumbnail`, which reads it in the process, as Dismas made it), as a cover read at a smaller size than its thumbnail is scaled down at each read, which took 8 times as long at the normal size once the covers had been zoomed in. Zooming the covers in past the size they were made at starts a quiet scan, which makes them all again, four at a time (`utils::in_threads`, with the loader's `READING_THREADS`; `ScanEvent::Covers` counts them for the progress bars), as each is decoded in glycin's sandbox; they're shown scaled up until then. Zooming back to the normal size starts one that makes them smaller, in a fraction of that time. GridView keeps hundreds of cells bound around the visible ones (`max-columns` × 30, plus a row before and after), and while the grid scrolls it binds many of them again at about every frame, as its anchor moves back and forth, but it hides the cells off screen (`gtk_widget_set_child_visible`, which unmaps them). So a cell only shows its cover while it's mapped: it's read on bind if the cell is mapped, or when it's mapped, and dropped when it's unmapped (`show_cover`). GTK only shows a cell within 10 pixels of the screen, so each cell coming on screen also reads ahead the covers of the albums a screenful before and after it into the cache (`read_ahead`; a screenful is the number of mapped cells, at most a third of the cache, so that the covers read ahead don't push out the ones on screen), which keeps the 150 most recent ones. A cover is read at the size the grid shows it at most, in the pixels of the monitor the window is on (`cover_pixels`), so a thumbnail made for a monitor with a larger scale is scaled down as it's read (`cover_image::read_thumbnail`, in the process, as Dismas made it from pixels decoded in the sandbox: GTK's loader decodes it, and each pixel is the average of those it covers, `area_downscale`, premultiplied for the PNG thumbnails with transparency, which took half the time `image`'s decoder and filters did); a change of scale reads the covers on screen again (`reset_covers`), and drops those still being read at the size before (`cover_generation`). Both happen right away, in the map handler: idle callbacks, even at `HIGH_IDLE`, don't run while the grid scrolls, as GTK keeps the main loop busy, so a read-ahead deferred to one ran 13 times in a whole scroll. Opening the grid reads the covers of the ~190 cells GTK maps before it hides the ones off screen, once. Counted on a library of 828 albums, scrolling the grid to its end and back read 14,695 covers before, and about 1,500 since, and 80% of the cells coming on screen found their cover in the cache; the rest waited a frame or two. Tracks without an album tag are grouped by the folder they're in (`album_folder`, where disc folders count as their parent), as an album named after it (`folder_album_title`), which `Track::album` shows too, and searches. Hidden files and folders aren't read (a drive's `.Trash-<uid>` keeps deleted tracks under their names), nor the recycle bins of Windows and of network drives, their snapshots and Synology's thumbnails (`is_library_entry`: `$RECYCLE.BIN`, `RECYCLER`, `#recycle`, `#snapshot`, `@Recycle`, `@eaDir`, ignoring case), and neither are they in added or dropped folders. Symbolic links are followed, by the scan as by added and dropped folders (`utils::read_folder_tree`), once the folders without them are read, and what a link leads to is skipped if it was read already, by its device and inode, so a link back into the music folder, or a loop, adds nothing; of two links to one folder, the first by path is read. Hard links aren't skipped, as two hard links to a file can be meant. A link that leads nowhere is skipped, and its tracks leave the grid until it's back, unlike a music folder that isn't there.
- **Search fields** (`audio/track/fields.rs`): each track's values for the fields of the search syntax are packed into one string of `code\tvalue\n` lines (`FieldParts::encode`, `FieldCode`), each value cut at 16 KiB, as the search text's items are (`MAX_SEARCHED_TEXT`), as the library reads the fields of every track at each search with a field, folded with `normalize_search_text` and written once: the title, artists, album (or its folder's name, `folder_album_title`, never the translated "Unknown album"), composers and their sort names, lyricists, arrangers, every performer credit as "name (role)" and the conductors, the performers of each kind of the Performers list, the roles, the work's names at every level (the WORK tag, its full title and the Work Hierarchy names), the movement, the collection, the forms (the plugin's MusicBrainz work types at every level, `WorkHierarchy::forms`), the catalogue numbers of the work or of the title (`CatalogueNumber::search_text`, e.g. "bwv 1047" or "op 2.4"), genres, grouping, labels, catalogue numbers of the release, release types, media, the file format, the MusicBrainz ids, the year, disc and track numbers, the recording, original and release dates as tagged, flags (`Flag`: movement, arrangement, live from the performance's attributes or a live release, partial, lossless from a bit depth), and the length (a CUE track's part, `CueTrack::length`), sample rate, bit depth, bitrate and channels. The library keeps them in its `fields` column, read with the properties (`ReadOptions::SCAN`), and the loader's workers make the queue's copy (`TrackData::fields`) from the same parts, so the two match exactly (`the_queue_and_the_library_encode_the_same_fields`). The codes are stored, so changing one needs a schema bump; `dismas_length` reads the `ln` line in SQL too. `normalize_search_text` folds case, accents, curly quotes (to `'` and `"`) and dashes and the minus sign (to `-`), and collapses whitespace, with a fast path for ASCII; `normalize_key_text` keeps the older fold without the quotes, dashes and spacing, for `composer_key`, as plays.db keeps the favorite works by keys made from it. The search blob also has each catalogue number as one word (`CatalogueNumber::word`, "bwv1047"). The catalogue numbers of the work's name, its full title and the title are each kept once, at their first place (`fields::catalogue_numbers`), with a set of those seen (`first_occurrences`): a crafted title named millions of them, and comparing each with all the ones before it took hours. Only the first 4 KiB of a name are read for its numbers (`MAX_NAME_LEN` in `catalogue.rs`), cut after the last whole word, and a number that the words past the cut could go on with is left out rather than read short: the parser keeps about 28 bytes for each byte of a name, and three crafted names of 16 MiB, lofty's limit for an item, took 1.27 GB.
- **The search syntax** (`search_query.rs`, with `lexer`, `parser`, `values`, `eval` and `print` in `search_query/`): one grammar for the search boxes and, later, the rules of smart playlists made by the user, read leniently (`Mode::Search`) or strictly (`Mode::Rule`), which reports every `Problem` so that a typo can't be saved as a search for plain words; `Problem::is_error` says which ones stop a search (it then matches nothing, `has_errors`) or a rule. Plain words and quoted phrases are found in the folded text of the tags, as before; `field:value` (names in `Field`, English, ASCII case ignored) contains, `=` is a whole value, `<`, `<=`, `>` and `>=` compare numbers, lengths and dates, and `a..b` ranges include both ends; `field:!=x` is `-field:=x`; `has:field` and `is:flag` (`IsFlag`) test presence and flags; `field:(a OR b)` applies the field to each value; NOT binds tighter than AND, and AND than OR (Strawberry's order). A term on a field without a value is false, and `-` makes it true. Dates are periods in local time (`2026-10`), and relative ones (`-30d`, `-2w`, `-1m`, `-1y`, months and years on the calendar) are moments, kept unresolved (`DatePoint::Ago`) until a search is matched, so that two parses of the same text are equal, which the album search's check for stale results needs; the queue's `SearchFilter` and the library's `Matcher` then work them out once, at the time the search starts (`Query::at`), rather than for each track. A bare one means since then. `m` is always months; lengths are `3:30`, `90s`, `5min`, `2h`. The lexer works on the raw text, so only ASCII `-`, `"`, `(` and `)` are syntax, and AND, OR and NOT only in capitals. A rule must quote `*`, `?`, `@`, `[` and `]`, and `field::` is refused, so that wildcards and regular expressions can get a meaning later without changing saved rules; unknown names are refused too, so adding a field never changes one. `sort:`, `pick:`, `limit:` and `by:` are rules' (`Directives`), and a search ignores them with a hint. `Query::to_text` prints the canonical form a rule is saved as, which parses back to the same query (`print_then_parse_is_identity`), and `SYNTAX_VERSION` goes with it. `Query::needs` says what to read for each track (`Candidate`: the text, the fields, the path, whether the file is gone, and what isn't in the tags: `added:` from the library's column, `plays:` and `played:` from plays.db's totals (`played:` is `last_played`, the last listen logged, as Recently Played goes by; `plays:` is 0 for a track never heard), `favorited:` and `is:favorite` from its favorites, `is:favorite-album` and `is:favorite-work` from its favorite albums and works, the latter with the works of favorite recordings, as the Works page's heart). `play_stats::search_stats` reads only what a query needs; the queue's `SearchFilter` keeps it, with the library's added time, album and work of each path (`library::track_entries`), in `QueueSources`, read as the search is typed and when a favorite is marked, and the library's `Matcher` reads it in the thread of the statement, by path. Tests never read the user's plays.db: the library's take theirs from `TEST_SEARCH_STATS`. `plays:3.. played:<-61d` gives exactly Not Heard Lately's tracks (`not_heard_lately_is_expressible_in_the_search_syntax`).

- **Music folders** (`music-folders`, edited in Preferences): an `a(ss)` of URIs, the folder that's read and, for one that came through the document portal, its host path, which names it and tells it apart even once the portal can't (access taken back, or the folder made again, which gives it a new doc ID). The library is read again when the Preferences dialog closes, if the folders changed (a scan can't be stopped, so a folder added by mistake isn't read); a scan asked for during another follows it (`rescan_pending`). A hand edit with `gsettings` applies at the next scan. With no album to show, the album page says why (`LibraryView::update_empty_page`, from `empty_page_text`): it names the music folder Dismas looked in, when there's one, or, when the library has albums in the unavailable folders (`library::has_albums` with only the folders left out hidden), says that the folders are missing or empty, as a missing `~/Music` at first run is unavailable too. Its Choose Music Folders… button (`win.choose-music-folders`) opens Preferences with the focus on Add Folder…, and takes the focus in place of the album search (`focus_search`), and from an empty search when the page shows (`update_stack`), as there's nothing to search; its accessible description is the page's, for screen readers.
- **Watching the music folders** (`FolderWatch` in `library/watch.rs`): each scan also returns the folders to watch (`folders_to_watch`: every folder it reads in the music folders on local disks, and in the folders that symbolic links in them lead to, without the hidden or left out ones), and `LibraryView` gives them to its `FolderWatch`, which keeps a GLib directory monitor for each, as they don't look into subfolders. Any change but an attribute's or a hidden file's (`changes_library`, as the scan doesn't read hidden files), and a drive mounted or unmounted (`gio::VolumeMonitor`) where a music folder is, or in one (`mount_changes_library`, from the music folders and the folders that links lead to, without symbolic links, in the scan's `WatchList`; while a music folder isn't there, or a link leads nowhere, any drive, as the folder a symbolic link leads to is only known once it's there), starts a quiet scan (`start_scan(false)`) once nothing changed for 2 s, as copying an album changes its files many times over. The scan doesn't wake it: reading files isn't watched. When a scan adds folders to those watched, another one follows, for files that came into them before they were watched. Folders on network shares (`filesystem::remote`), whose changes can be made from other computers, and those that came through the document portal aren't watched; while one of them is there (`ScanResult::unwatched`), showing the album grid starts a scan (`scan_unwatched`), unless the last one finished less than 5 minutes ago (`UNWATCHED_RESCAN_INTERVAL`), as reading a network share or the portal's folders takes a while, and going back and forth between the pages would read them each time. Scan Now, in Preferences (`win.rescan-library`, also Ctrl+R, the HIG's Reload, and F5), is the fallback for changes that weren't seen, and has taken the place of the main menu's Scan the Music Folders.
- **Playlists:** one playlist is selected at a time (the `selected-playlist` setting, empty for the queue). Its tracks are loaded into the player's single `Queue`, which plays them and receives added tracks. Switching stops playback and reloads the `Queue` from the other playlist's file. All playlists are M3U8 files written and read by `playlists.rs`, in the order of their tracks: the queue is `~/.local/share/dismas/queue.m3u8`, and saved playlists are in `~/.local/share/dismas/playlists/`. A name that `check_name` wouldn't allow has no file (`path_in` returns `None`): names also come from the settings and from `win.selected-playlist`, which GtkApplication exports on the session bus, and "../x" would reach other files. Names are at most 243 bytes, as GLib writes to a temporary file named `<name>.m3u8.XXXXXX` first. Shuffling reorders the selected playlist and saves it, keeping the order from before in `~/.local/share/dismas/unshuffled/` (`queue.m3u8`, and `playlists/<name>.m3u8`, so a playlist named "queue" has its own) until the shuffle button is turned off, which puts it back by URI, with the tracks added since at the end. The button shows whether that file exists, for the selected playlist: it's synced from it (`sync_queue_shuffled`) on switching playlists and when the queue empties, and only the button and its shortcut go through the `queue-shuffled` setter, which shuffles or restores. The playing track, or one paused partway, stays first; otherwise the first shuffled track is made current. The file is written before the shuffled playlist, and removed after the restored one is saved, so a crash can't lose the order. It follows renames, goes with deletes, is copied by Save as Playlist, and is dropped when the tracks are replaced (Remove All, the Play buttons, playing dropped files, files opened at startup); the Undo of Remove All puts it back, unless the playlist was shuffled again since, and the Undo of a replaced queue puts the queue's back. Sorting a shuffled playlist drops it too, and the sort's Undo puts it back. An album's Play buttons and a click on one of its tracks (`play_shown_tracks`) only have that Undo when the queue had tracks that the new ones leave out (`ReplacedQueue::loses_tracks`), as a click on another track of the album that's playing loses nothing, and the tracks are mostly clicked for that. They're listed on the Playlists page (`playlists_page.rs`). Add to Playlist ▸, in the track menu, the album menu and the menus of the Add buttons (`Adw.SplitButton`s, whose action groups `setup_library` inserts and whose menus `update_playlists_menu` makes again with the playlists; libadwaita has no pill split button, so `style.css` styles `splitbutton.pill`), adds tracks to a playlist other than the selected one without switching to it (`Window::add_to_playlist` in `window/adding.rs`), as switching stops playback: `playlists::append` writes them at the end of its file. The selected playlist isn't in that menu, as it has an item of its own that goes through the queue, which would write over its file. Appending is refused while tracks are read (`loads`), as the file of a playlist being switched to was read already and would be saved without them; it shifts no resume point, and restoring the order from before shuffling puts them at the end. New Playlist… in the same menu makes one with the tracks (`create_with_tracks`), also without selecting it; the toast's Open switches to it. Importing reads any M3U file, resolving relative paths against its folder and keeping only the tracks found. Playlists are decoded like CUE sheets (`cue_sheet::decode`), as Windows players write `.m3u` in its legacy encoding. Import (`import_m3u`) also looks for the tracks that aren't where it says (`Finder`): a path written in another case, and the end of an absolute path from Windows or another computer, in the playlist's folder, then in the music folders with at least a folder and a file; Dismas's own playlists don't, as their missing tracks are placeholders. A playlist that's imported or opened is turned down, rather than read in part, when it's over 32 MiB or names more than 200,000 tracks (`MAX_PLAYLIST_SIZE`, `MAX_PLAYLIST_ENTRIES`), as a file of short lines would make millions of entries; Dismas's own playlists (`read_m3u`) have no limit, as one that couldn't be read would be saved again without its tracks. Exporting writes paths relative to the folder of the file for the tracks under it, so the playlist can be copied with the music to another device. Files dropped on the window go by where they're dropped. A single drop target, on the window's drag overlay (`drag_overlay.rs`), takes them all and works out at each motion what a drop there would do (`file_drop_at` in `window/loading.rs`): on X11 the widgets aren't told the drag left once it's dropped, so a second target that took the drag without getting the drop would keep it and turn the next one down. On the playlist pane, the files go between the tracks where the reordering line shows, or at the end where there's none (on the album's tracks), which the pane's outline shows. Above the first movement of a work, which would be under its header, they go before the work: the line is under the row before it, or above the header of the work at the top. Elsewhere, the overlay shows two zones over the main area: a large one that adds the tracks to the selected playlist, and one below it that plays them in place of the queue, like an album's Play button, with an Undo on the toast that puts back the queue and the playlist that was selected (`undo_replace`). The zones are laid out beside the pane, over the part of the main area that shows: next to the sidebar of the collapsed split view, the content is only drawn moved aside (`PushBin`). There's no modifier key for playing, as the app the files are dragged from reads the keys, and on Wayland Dismas can't see them. Each album of the grid has a menu (`setup_album_menu`, a right click or a touch long press, and `Window::show_album_menu`), with Play, Play Next, Add to the selected playlist and Add to Playlist ▸, which on an album selected in selection mode take all the selected albums and leave selection mode, like the buttons of its bar; it also has Add Album to Favorites (Add Albums to Favorites on the selected ones, and Remove when they all are favorites already; not among the covers of a work, whose heart is a favorite recording's), and on an album of its own, Open Directory and its booklets. Albums are dragged from the grid the same way (`setup_album_drag` in `library_view.rs`), a selected one in selection mode taking the other selected ones, as an `AlbumDrag` that only Dismas takes; they only go to the pane, which is shown while they're dragged if it was hidden, and hidden again if they aren't dropped. Esc cancels the drag, as for tracks, through `utils::cancel_drag`. On X11 without a compositor, the window's input shape is set to its size after each resize (`setup_x11_drop_shape`): GTK's X11 drag sources cache the shapes of the windows, and a window without one never tells them it grew, so drags over the part added by widening the window went to the window below.
- **Smart playlists** (Recently Played, Most Played and Not Heard Lately, on the Playlists page) come from the play stats (`play_stats.rs`), in `~/.local/share/dismas/plays.db`. It's a database of its own because the library's is a cache whose schema bumps drop the tracks, and the history can't be read again from anywhere: its tables are never made again, a later version only changes them in place, and a version newer than the build knows is left alone. The player's `ListenTracker` measures each listen from the positions it's given (whole seconds, four times a second): a step of 1 or 2 s while playing is heard, and anything else (seeks, resume points, going back) only moves the last position. `show_track` ends the listen and starts one for the new track, `clear_current_track` ends it, and so does the end of the queue. Ending keeps the track, so playing it again without `show_track` (`start_over` on a one-track queue, or Stop then Play) is a new listen. A listen is logged from 30 s, or half of a shorter track, and counts as a play (`counted`) from half the track or 4 minutes, whichever is less, as on Last.fm. A track of unknown length needs 30 s and 4 minutes. Listens are written in GLib's pool when they end. On quitting, and before a smart playlist is read, the listen to the track playing is written right away (`save_listen`), so that it's saved, and on the list. Each write adds to the track's all-time `totals` (plays, seconds heard, last played) and drops the listens older than a year. Tracks are told apart by their URI, so a moved file starts again. Recently Played is the last 100 tracks logged, played oldest first, in the order they were last heard, so that a work's movements keep their order; Most Played is the 100 with the most plays in the last 182 days; tracks with the same number of plays are in the order they were last heard, so that a work heard through keeps its movements in order too. Not Heard Lately is like Spotify's Repeat Rewind: the 100 tracks with the most plays all time (from `totals`, so plays older than a year count), at least 3, whose last listen logged, even one that didn't count as a play, is over 61 days old; with as many plays, the ones unheard the longest come first and are kept. Its name avoids "favorite", which means the tracks marked with the heart. Opening one reads the list from the database at that moment, as a snapshot that doesn't change afterwards, and plays it in place of the queue, like dropped files (`play_in_place_of_queue`), with the same Undo, so it's never the selected playlist. Shuffling reads the stats too: each track's all-time plays and when it was last heard (`track_stats`, from `totals`), on the main thread, as the shuffle also saves the playlist there. The history can be turned off and cleared in Preferences. Off (`keep-play-history`), the player drops each listen as it ends (`finish_listen`), and the history so far stays, for the smart playlists and the shuffle. Clear History (`win.clear-play-history`, installed on the class rather than added to the window, so that other programs can't activate it over D-Bus; the window asks first, over Preferences) deletes the listens and the totals but not the favorites, with `secure_delete` and a checkpoint that empties the log, and forgets what was heard of the playing track (`forget_listen`). A listen still being written in the background when it's cleared is dropped: each is recorded with the history's generation when it ended (`history_generation`), which `clear_history` bumps first, and `record` checks it once its write transaction has the database. **Favorites** are in `plays.db` too, as they can't be read again from anywhere either: the `favorites` table, added in schema version 2 (the `CREATE TABLE IF NOT EXISTS` of the schema adds it to a version 1 database), keeps each track's URI and when it was marked. The heart button right of the Sleep Timer (`win.favorite`, a property action on the window's `track-favorite`), Ctrl+D and the track menu mark and unmark them; the heart is filled and red, whatever the accent color. `sync_track_favorite` reads whether the playing track is one each time the track changes. They're read and written on the main thread, as each is a single row; if they were written in GLib's pool, like the listens, two clicks close together could be written in the wrong order. The Playlists page has no list of them, to keep it short: the heart beside the album search shows them on the Tracks page, where Select All and Play play them. **Play a Random …**, in the album pages' menu (`win.play-random`, a section of its own under the zoom row, the `page_items` of `utils::setup_primary_menu_button`, kept in `LibraryView`'s `random_menu`; `play_random` in `window/smart_playlists.rs`), is one item that names what the page shows (`update_random_item`, at each page change): Play a Random Album, Play a Random Track or Play a Random Work. It plays one picked at random from what the page shows, in place of the queue, with the same Undo and a toast that names it (`play_announced_in_place_of_queue`), and nothing afterwards follows the search. What it picks from is what the page's search, composer and performer picked, and heart ask for (`LibraryView::random_pool`, from `wanted_filter`, a `RandomPool`), resolved in the worker, as the grid and the works are searched with it: what the page shows is still the other page's just after a page switch, or while a search is read. On Albums, an album with a track the filter matches (`library::search_albums`, every album without a filter), whole, from `library::album_track_paths`; on Tracks, a track the filter matches (`library::matching_tracks`), named by its title or else its file's (`title_from_file_name`), even a lone movement; on Works, a work the list shows, then one of its recordings that the filter matches (`library::work_recording_candidates`: the works of `listed_works`, which `works_of_rows` counts the recordings with too, so the two agree, with the recordings of the arrangements listed under each), played in the order of their album. Each is picked by the shuffle's weight (`shuffle::weight`: when the last of its tracks heard was, and the plays of the one played the most) with `shuffle::weighted_pick`, outside the hidden folders, without the one it played last on that page (`last_random_album`, `last_random_track`, by URI, and `last_random_work`; `pick_index`), so that choosing it again plays another. A work is picked twice over (`choose_work`): first the work, by the weight of the tracks of all its recordings, those the filter doesn't match too, so that a work heard lately in any recording is less likely, then one of its recordings, by the weight of its own tracks, so that the recordings of a work take turns. Both are also weighed by their length: the work by that of its longest recording that the filter matches, and the recording by its own, so that a 40-minute work is ten times as likely as a 4-minute one, and a whole recording more likely than an excerpt of the same work; with every work as likely, collections of short pieces crowded out the rest, and the music stopped after a few minutes most of the time. The lengths are read only for it (`Lengths::Read` in `query_work_rows`, as reading `fields` takes time the Works list doesn't need to spend), and a recording's is that of its tracks, those not known counted as long as the others (`RecordingCandidate::length`); one with no length known counts as the median of the known ones, and with none known they all count the same (`median_length`, `counted_length`), as a weight of 0 is never picked. Length spans far more than the play history's weight does, so in a library of operas and songs, the operas get most of the picks: that's the share of the time they take. The toast names the work, and says when the recording is only part of it ("Playing part of …", `RecordingCandidate::single_movement`: all its tracks at one place of the work, such as an aria of an opera on a recital, which a recording of a work as a whole or of movements at unknown places isn't), or else an arrangement listed under it, with what it is (`RecordingCandidate::arrangement`, as `WorkRecording` has it; `Part::of`). With the heart on, the works are the favorite ones as the list counts them (`WorkInfo::is_among`, which `update_works` marks them with), and the recording is a favorite recording of the work if it has one (`play_stats::favorite_recordings`), or else one of a work marked, the work itself or an arrangement listed under it, as an arrangement marked makes the work it's listed under a favorite. **Favorite works and recordings** are in `plays.db` too (schema version 3 adds `favorite_works`, by the library's work key, and `favorite_recordings`, by the work key, the album id and the URI of the recording's first track, as a recording has no id of its own and an album can have two of a work). Works are marked from the menu of a work's header (`add_work_items`, which looks the work up with `library::track_work`) and of a row of the Works page (`show_works_row_menu`, the rows' `work-menu-requested`, with the Menu key through each row's `work-row.menu` action, as keys go to the list), and recordings from the menu of a cover of an open work (`show_album_menu`). The Works page reads them with the works (`WorkInfo::favorite`, set by `WorkInfo::is_among`, a heart on the row, which a work with a favorite recording gets too, and a work with an arrangement that's a favorite), and the covers of the favorite recordings have a heart (`work_covers`, on the main thread); the heart beside the search (see The album grid's search) shows only those; marking one reads the works again (`refresh_favorites`). The Playlists page has no list of them: the heart beside the album search shows them on the Works page. **Favorite albums** are in `plays.db` too (schema version 4 adds `favorite_albums`, by the album id, with the URI of the album's first track and when it was marked). An album's id changes with its tags (it's the MusicBrainz release id, or else made from the title and the album artist), so the URI finds the album again: at each reload of the albums (`LibraryView::reload`), a favorite whose id isn't among the albums read moves to the album its first track is in now (`favorite_album_updates`, written by `play_stats::update_favorite_albums`), unless that's the same id, as for an album in a folder that's hidden. The URI is NULL until it's looked up in GLib's pool after marking (`LibraryView::favorite_albums_changed`), so that marking never waits for the library, and the reload looks up any left. The reload reads the favorite ids again on the main thread once the moves are written, rather than keeping the ones read in the pool, which would miss an album marked meanwhile; they're `LibraryView`'s `favorite_albums`, which set each `Album`'s `favorite` property (`apply_favorite_albums`, also when the albums read are the same, as the grid then keeps its `Album`s). The grid's cells bind it to their heart (`AlbumCell`'s `favorite`, which the covers of a work set for a favorite recording instead). Albums are marked from the album menu (`Window::mark_favorite_albums`) and from the heart in the header of the album pane, which emits `favorite-toggled` on a click only, as `AlbumTracks::show_favorite` also sets it for an album marked from the menu. The heart beside the album search shows only them on the Albums page (see The album grid's search), and marking one while it does searches again. The Playlists page has no list of them either: the heart beside the album search shows them on the Albums page, where Select All and Play play them whole. A retag that also moves or renames the first track's file loses the mark, as moving a file loses its mark as a favorite track and its play stats.
- **Pages:** the player, the albums, the tracks (the same grid, see The album grid's search), the works and the Playlists page take turns in the main area, with Ctrl+1 to Ctrl+4 and Ctrl+P. Each header has the same `PageSwitcher` (`page_switcher.rs`), whose buttons drive the window's `page` property through the `win.page` action. Its playlist pane toggle sits on the left, apart from the page buttons. Its Player button follows `player-available`, which is false while there is nothing to play. Where a header bar is too narrow for the page buttons, the switcher folds them into a menu button during allocation (`set_child_visible`), and measures only the folded width as its minimum; the page titles are in a `FitBin` (`fit_bin.rs`), which hides its child where it doesn't fit. With the album grid's single column, that keeps every page within the 360-pixel minimum, whatever window buttons the desktop shows.
- **Restoring at startup:** a selected saved playlist always reopens. "Restore Queue at Startup" (the `restore-playlist` key, named after Amberol's) only decides whether the queue keeps its tracks; without it, the queue starts empty. Opening Dismas with files replaces the queue. A reopened playlist resumes, paused, from its point in the `resume-points` setting (`resume_point.rs`), and so does a playlist switched back to: by playlist name, the track's URI and its index in the order the tracks were added, and the position. The `Application` saves the selected playlist's point, since it outlives the window, when playback pauses, stops or changes track, when the queue changes, every 30 s while playing, and on quitting (SIGTERM quits too). Switching saves it right away, in `replace_selected_playlist`, as the save at idle would come after the switch. Renaming a playlist moves its point, deleting drops it, and startup drops those of playlists that are gone. Resuming shows the track paused without getting the pipeline ready: `GstBackend::resume_at` keeps the position and seeks when the track plays. A pipeline got ready to play, paused, would keep its position stuck once it played (see Pausing a track that hasn't played).
- **Command line** (`Application::command_line`, with `HANDLES_COMMAND_LINE`): the first Dismas gets the arguments and switches of each `dismas` run, with relative paths resolved in the folder it was run in. Plain files go to `open`, which D-Bus Open from file managers uses too (an M3U playlist among them gives its tracks, through `import_m3u`, in `audio_files`, as the desktop file claims `audio/x-mpegurl`; Add Tracks… and Add Folder…, in the main menu, add files through the same `add_files_to_queue` with `QueueMode::Show`, as a phone has nothing to drag them from; their dialogs start in the first music folder that's there, `start_in_music_folder`): at startup they replace the queue, leaving the pane as it was, and in a running Dismas they're added to the selected playlist, bringing up the window. `--add` adds them to the end of the selected playlist without bringing up a window that's there, hidden or not, and leaves the page and the pane as they are (`QueueMode::Quiet`), so scripts can add tracks while the user does something else. `--play` plays them in place of the queue, like the drop zone (`play_in_place_of_queue`, with its Undo). If Dismas isn't running, both start it by restoring the selected playlist, and then wait until the playlist's tracks are in the queue (`Window::after_startup`): tracks are read in other threads, so tracks read while the playlist loads would land in the middle of it, and the playlist would be saved without its own tracks. Giving both switches is turned down in `handle_local_options`, in the process that was run.
- **Migrating from Amberol:** on the first run (no library, queue or playlists in `~/.local/share/dismas` yet), `migrate.rs` copies them from `~/.local/share/amberol`, through temporary files, and copies the settings changed in the `io.bassi.Amberol` schema if it's installed. The `amberol-migrated` key records that it ran, so clearing the data folder doesn't bring Amberol's settings back. Caches aren't copied; they're made again.

### Translations

- UI strings use gettext helpers from `src/i18n.rs` in Rust, and `_()` / `C_()` in Blueprint.
- `po/*.po` files came from upstream's translators (GNOME's Damned Lies). Don't rewrite them wholesale; when a source string changes, keep the edit to the affected entries. Translations that couldn't follow the rename from Amberol are marked fuzzy. New translatable files go in `po/POTFILES.in`.

## Conventions

- Commit messages: a one-sentence summary line of at most 72 chars, capitalized, with no trailing period. Then a blank line and a prose body explaining *why*. Use `Closes #N` / `Fixes #N` for issues.
- Dismas never writes to music files; it only reads them. `clippy.toml` bans lofty's write API: the `WriteOptions` type that every lofty write takes, and the write methods themselves, for calls that pass `Default::default()` and never name the type. CI runs clippy with `-D warnings`, so a write fails the build. Tests write their tags through `utils::write_test_id3v2`, the only exception.
- The UI calls audio files "tracks" (not "songs"). Keep the freedesktop icon name `media-playlist-repeat-song-symbolic` as is.
- Every UI change works for keyboard, touch and screen-reader users. Each action has a keyboard path: menus open with the Menu key (`utils::setup_menu_key`), drags have a key or a menu item, and a key that a focused widget uses isn't an accel (see Keyboard shortcuts). A right click or hover has a touch equivalent, a touch-only long press, and a gesture in a scrolled list acts when it's let go of (see Touch). Custom widgets, and buttons that repeat on each row, get accessible names (see Screen readers). When checking a change, read the names that AT-SPI gets too. Touch can't be tried on a device here, so touch code keeps to what GTK's gesture rules document.
