# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Upstream policy on AI contributions

This repository is a fork. The upstream project (gitlab.gnome.org/World/amberol) **does not accept contributions generated by LLMs**, and its contribution guide names Claude explicitly. This covers code, docs, issues and artwork. This fork's own CONTRIBUTING.md welcomes AI-assisted work, but none of it goes upstream. Don't prepare merge requests, issues or other upstream submissions from AI-generated work.

Flathub has a similar policy (the Generative AI policy in docs.flathub.org's requirements): a Flathub manifest must not contain AI-generated or AI-assisted content, AI tools must not open a submission or write its description, commits or replies, and AI-generated code in the app must be disclosed. Don't write a Flathub manifest or prepare a Flathub submission. The manifests in this repository are for building the app outside Flathub.

## Build and run

Dismas is a GTK4/libadwaita music player written in Rust, forked from Amberol. The app ID is `io.github.dachshund7.Dismas`. Build it with Meson, which runs Cargo itself. A plain `cargo build` fails until Meson has generated `src/config.rs`.

```sh
meson setup _build                     # add -Dprofile=development for a debug build with the .Devel app ID
meson compile -C _build                # or: ninja -C _build
meson devenv -C _build ./src/dismas    # run uninstalled
```

- **Generated `config.rs`:** `meson setup` writes `src/config.rs` from `src/config.rs.in` and copies it into the source tree. The file is gitignored. Cargo, rustfmt and clippy all need it to exist.
- **Profiles:** the default profile builds `--release`. Cargo's target dir is `_build/src/`.
- **Runtime dependencies:** gtk4 ≥ 4.19.5, libadwaita ≥ 1.8, GStreamer ≥ 1.20 (incl. plugins-bad), and the glycin loaders (`glycin-loaders`, plus `bwrap` outside Flatpak) to decode cover art. At build time: `blueprint-compiler`, `msgfmt` (gettext), the SQLite development files for the library database (rusqlite links against the system SQLite), and the libseccomp and fontconfig development files, which glycin links against.
- **Flatpak:** there are two manifests, which differ only in the app ID, the profile and the Devel one's debug variables; keep the rest the same. `io.github.dachshund7.Dismas.json` builds the regular one, which the releases ship, and `io.github.dachshund7.Dismas.Devel.json` the Devel one, which CI builds on each push. With their own app IDs, the two can be installed side by side. Both build on the GNOME 51 runtime from the folder they're in (a `dir` source, skipping the build folders), and let Cargo download the crates during the build (`--share=network`). They read the Music folder through both `xdg-music:ro` and `~/Music:ro`: where no `~/.config/user-dirs.dirs` sets `XDG_MUSIC_DIR`, as in many window manager sessions, `xdg-music` shares nothing, while Dismas falls back to `~/Music` (`library::default_music_dir`). A file that came through the document portal (opened, dropped, or in a music folder added outside the Music folder) has a path under `/run/user/<uid>/doc/` in the sandbox, and its path outside it (`utils::ATTRIBUTE_HOST_PATH`) only names it: Open Directory (`open_track_directory`) gives `gtk::FileLauncher` the sandbox path, as the launcher opens the file and the portal works out its folder outside, while the host path can't be opened inside the sandbox. Inside the sandbox, the data is under `~/.var/app/<app ID>/`, so there's nothing to migrate from Amberol.

## Checks

GitHub Actions (`.github/workflows/ci.yml`) runs these on pushes to main and on pull requests. The `lint` job runs `checks.sh` and `reuse` on Ubuntu, and the `advisories` job checks Cargo.lock against the RustSec advisory database (`cargo deny check advisories`, set up in `deny.toml`), so a new advisory can fail it without a change to the code. The `build` job builds the app with Meson and runs clippy, the tests and the data file validation in a `fedora:latest` container, because Ubuntu's GTK and libadwaita are too old. The `flatpak` job builds the Devel manifest in the `ghcr.io/flathub-infra/flatpak-github-actions:gnome-51` image and uploads `dismas-devel.flatpak` as an artifact. `.github/workflows/release.yml` builds the regular manifest the same way when a release is published on GitHub, and attaches `dismas.flatpak` to the release; run by hand, it only uploads the bundle as an artifact. As it can write to the repository, its actions are pinned to commits, with the release each one is in a comment; update them by hand. To try the `build` job locally, run its commands in `podman run fedora:latest`; the `flatpak` job, with `flatpak-builder` in that image (`podman run --privileged`).

```sh
cargo fmt --all -- --check                  # needs src/config.rs; a blank line is enough (CI writes one)
cargo clippy --all-targets -- -D warnings   # keep it free of warnings
cargo test                                  # unit tests are in #[cfg(test)] modules next to the code
cargo test <name>                           # a single test
build-aux/checks.sh                         # fmt, typos (configured in .typos.toml), POTFILES.in, resource order
reuse lint                                  # REUSE/SPDX licensing; needs reuse ≥ 4, older ones ignore REUSE.toml
cargo deny check advisories                 # the dependencies against the RustSec advisories
```

Every source file needs SPDX headers (`SPDX-FileCopyrightText` / `SPDX-License-Identifier`). REUSE.toml covers files that can't carry headers.

## Architecture

### Audio: message passing between threads

`src/audio.rs` has a header comment explaining the design. GStreamer and the controllers can fire from other threads, so nothing touches the UI state directly. Everything goes through async channels:

- `AudioPlayer` (`audio/player.rs`) is the hub. `Application` (`application.rs`) owns it and gives it a sender for `ApplicationAction`s.
- `GstBackend` wraps GstPlay and reports changes over a channel.
- Gapless playback goes around GstPlay, whose `set_uri` stops the pipeline. The player publishes the next track (`update_next_track`), as a `TrackSource`: the track's URI, which tells tracks apart, and the audio file's, which plays. On playbin's about-to-finish, the backend hands it to playbin, one track at a time. On stream-start it sends `TrackAdvanced`, and the player follows without touching the pipeline. Without a hand-over, EOS leads to `PlayNext` as before. GstPlay changes the pipeline's state and loads tracks on its own thread, and stopping or starting it while a track is handed over can hang GstPlay, so the hand-over is skipped while the playbin's state lock is held, while a load is pending (counted until each `uri-loaded`), and within 500 ms of the last load (rapid skipping). A generation number lets the player ignore switches from before it loaded a track. `stop` loads the track again, since uridecodebin3 would keep a track that was handed over. rgvolume only resets on EOS, so the ReplayGain bin sends it an EOS of its own at each stream-start and drops it after rgvolume.
- Controllers implement the `Controller` trait (`audio/controller.rs`) and are pushed state changes by the player:
  - `MprisController`: media keys and desktop integration.
  - `InhibitController`: prevents suspend during playback.
  - `TrayController` (Linux/FreeBSD): a StatusNotifierItem through ksni, which runs on a thread of its own, so the tray sends `ApplicationAction`s (`ToggleWindow`, `Present`, `Quit`) and `PlaybackAction`s. It's shown while `background-play` is on, and waits for a tray host if there's none yet. Its icon is a simple blue one of its own (`<app ID>-tray`, installed renamed from one source for both profiles), since the app icon is too detailed at tray sizes. It isn't symbolic, as trays would recolor it. The app ID prefix lets Flatpak export it to the host. Clicking it closes the window if it has the focus, or if it's on screen and nothing covers it (with focus following the pointer, moving to the tray focuses other windows), and presents it otherwise (`closes_on_click` in `application.rs`). GTK knows neither about desktops nor about other apps' windows, so on X11 `x11_stacking.rs` asks the window manager, through x11rb rather than Xlib, whose default error handler would end the process when a window closes during the check: the window is on screen if it's viewable (window managers unmap other desktops' windows), and covered if a normal window above it in `_NET_CLIENT_LIST_STACKING` overlaps it. On Wayland, apps aren't told about other windows, so a window that isn't minimized or suspended always closes. Presenting a window that's on another X11 desktop moves it to the current one (`present_main_window`). The menu's Show Dismas only presents. Scrolling steps the volume (`PlaybackAction::StepVolume`, by `VOLUME_STEP` like the slider). Trays disagree on the direction: Plasma sends Qt's wheel angle (up positive, 120 a notch, less from touchpads), and waybar and others send steps with down positive. ksni hides the one difference in the call ("Vertical" against "vertical"), so `XDG_CURRENT_DESKTOP` containing KDE picks Plasma's way. Upstream snixembed sends no direction (0) and no middle click.
- **Background playback:** while `background-play` is on, the `Application` holds itself, so closing the window keeps the music playing. Closing then only hides the window, which comes back as it was, without a new `Window` reading the albums again; turning the setting off closes a hidden window, so Dismas quits. The hold is taken before asking the Background portal, and only a refusal drops it and turns the setting off. Many sessions have no Background portal (window managers, or a portal frontend with only -gtk, -wlr or -hyprland), and an error there keeps the hold.
- Controllers and the UI ask for things by sending `PlaybackAction`s back to the player.
- `PlayerState` is a GObject whose properties the UI binds to. It is only mutated on the main context.
- `Queue` is the list of tracks to play, a `GListModel` of `Track` GObjects. Shuffling reorders it for real (`Queue::shuffle`), so the order shown, the order played and the order saved are the same. The order is random, but it goes by the play stats (`audio/shuffle.rs`):
  - Each track has a weight, and a track with more weight is more likely to come earlier (Efraimidis and Spirakis's weighted random order).
  - A track heard just now has a tenth of the weight of one never heard, and gets halfway back in a week.
  - A track with 10 plays or more, all time, has twice the weight, so tracks played often but not heard for a while come early.
  - The movements of a work that are next to each other move together, in their order, as the queue's headers group them (`work_sections::continues_work`; see Works below), so each Prelude and Fugue of the WTC moves as one.
  - The same artist (for a movement, its composers) doesn't come twice in a row. The exception is an artist with more tracks than all the others together: its runs are then kept as short as they can be (`Spread`), rather than left to pile up at the end.
- Covers are deduplicated across tracks of the same album through a global `CoverCache`. Each cover has a `OnceLock` slot, so it's decoded once even when several of its tracks load at the same time. The tracks hold the slots (`AlbumCover`), and the cache keeps only weak references, so a cover is freed once no track has it.
- Cover art comes from the tags and could be crafted, so `cover_image.rs` decodes it with glycin, in sandboxed loader processes. Only the decoded pixels are scaled, color-picked and saved (as PNG, or as JPEG for the album grid) in the app. Decoding blocks, so it never runs on the main thread.
- **Tracks:** `audio/track.rs` has `TrackData`, the tags and file details of a track, and `Track`, the GObject the lists show; `audio/track/` has the rest: `credits.rs` (`TrackCredits`, and how the performers and composers are shown), `search.rs` (the text searches look into), `tags.rs` (`read_file_tags`, `ExtraComments`, and `file_tag`, the tag a file's tracks take, which the queue, the library and the covers all read), `work_hierarchy.rs` (the Work Hierarchy plugin's tag), `file_name.rs` (titles and albums from file and folder names) and `loader.rs` (`load_tracks`, and reading the tracks of a file).
- Tags and covers are read in up to four worker threads: `load_tracks()` (`audio/track/loader.rs`) sends the `TrackData` of each file over a channel, in the order of the files, all the tracks of a file at once (none, one, or a CUE sheet's), and the main thread wraps them in `Track` GObjects, which are not `Send`. The tag reader can panic on a malformed file, so every read of untrusted files (the loader, CUE claims, the library scan, thumbnails) goes through `utils::guarded`, which catches the panic and falls back; the scan stores such a file as a track without tags, in no album, so it isn't read again until it changes. Lengths over 1000 hours count as unknown (`sane_duration`), as GStreamer's and MPRIS's times can't hold what a damaged header reports, and seeks are worked out in seconds with saturating arithmetic (`seek_destination`).
- **Tracks whose files are missing** (`TrackData::missing`, the `missing` property): when a playlist or the queue loads (`load_tracks` with `placeholders`), a file that gives no track becomes a placeholder named after its file (`placeholder` in `loader.rs`), which keeps its place and is saved with the others, so a playlist opened while a drive is unplugged doesn't lose its entries at the next edit. Its reason (`Missing`) is that the file isn't there, or that it is but couldn't be read (damaged, or not allowed to be opened), which its row's subtitle says; an audio file that a CUE sheet among the files splits gives its tracks there, and has none. The queue's navigation (`next_pos`, `previous_track`, `is_first_track`, `is_last_track`, `playable_from`) skips them, and so do resuming and starting over; their rows are greyed out (the `missing` class), and activating one says so. After each scan, `reload_changed_tracks` reads them again, and they become tracks once their files are back. Added, dropped and album tracks don't make placeholders.
- **A track that fails to play**: GstPlay stops on an error. `GstBackend` forwards it as `TrackFailed`, unless a load is pending, as the error then belongs to the track before it, and gives the URI of the track handed over gaplessly if that one failed; the player only follows it if it's still the next track, and otherwise goes on as at the end of the track. The player emits `track-failed` on `PlayerState` and goes on to the next track if it was playing (`after_failure`); it stops when nothing follows, when it was paused, when the next track already failed since the last one that played (`failed`, cleared by a position), so a dead queue on repeat doesn't loop, or after 3 failures in a row (`MAX_FAILURES_IN_A_ROW`), as a broken audio output fails every track and would run through the playlist. The window says so in a toast, which takes the place of the one about the track before (`failed_toast`), and greys out the track if its file is gone (`Track::mark_missing`).
- **Works** (`WorkHierarchy::labels` in `audio/track/work_hierarchy.rs`): a track is a movement when its tags name a work and a movement, and the queue and the album view show a header over the movements of each work (`work_sections.rs`). Picard's Work Hierarchy plugin writes a JSON tag, which Dismas prefers to the work and movement tags: a Vorbis comment, an APEv2 item in Monkey's Audio, WavPack and Musepack files, an ID3v2 `TXXX` frame in MP3, AIFF and WAV files, or a `----:com.apple.iTunes:` atom in MP4 files (`ExtraComments`). The plugin makes the decisions, so they're right in every player, and Dismas only shows them. It picks the work in each path (`work_index`): the top-level one, unless a part of it has a catalogue number of its own, one the works above it don't have. So each Prelude and Fugue of The Well-Tempered Clavier (BWV 846 and on) is a work, but Book I and the acts of an opera aren't, and a whole Prelude and Fugue in one track is a work of its own, not a movement. Dismas names the levels below the work with the numbers their titles give them (`numeral`), and the movement with its number (`number`) unless its name has its own. A tag without `work_index`, from an older version of the plugin, leaves the work and movement to their tags. The header shows the work's own name, and Track Information its full title (`work_title`), with the collection. The movements of a work next to each other share a header (`continues_work`) when they share the work's composers (`work_composers`, from the hierarchy, or else the track's composers or artist), as a movement can credit others too: the author of the hymn in a Bach chorale, or Süßmayr in the Requiem. They must also come from the same release (`release_key`: the MusicBrainz release, or else the album and album artist), each later on the album than the one above it (`follows_on_album`, by disc and track number, or else any other track), so two recordings of a work one after the other, or a work added twice, get a header each. The header still shows the first movement's own composers, as MusicBrainz sometimes credits a work to someone else (Bach's BWV 981 to Marcello, whose concerto it arranges). When a movement is in several tracks, MusicBrainz links them all to it and marks the links "partial", so the hierarchy names them the same ("1. Ouverture" for both halves of the Royal Fireworks overture). The plugin reads the part each track has from its recording's title (`excerpt`, "Ia. Overture – Adagio"), which Dismas shows in place of the movement's name, numbered the same way; a recording's title can number a part without a dot, as in "3 Sarabande".
- **CUE sheets** (`cue_sheet.rs`) split an audio file into tracks: a `.cue` file next to it, or a `CUESHEET` tag (a Vorbis comment, or an APEv2 item for Monkey's Audio, WavPack and Musepack, which `read_tagged_file` reads into `ExtraComments`). A track of a sheet is at a path under the sheet, `Album.cue/track03` (or `Album.flac/track03` for an embedded sheet), which can't be a file, so the queue, playlists, resume points, unshuffled orders and the library keep it like a file's path; `Track::audio_file()` is the file that plays, and `Track::segment()` the part of it. A sheet only splits the files it has two or more tracks in (multi-file rips keep their own tags). The sheet that splits a file is the same however the file was reached: in a list of files, the first `.cue` that splits it (`Claims`), otherwise the first in its folder, otherwise the embedded one. Its tags are the audio file's, minus the ones about the whole file, with the sheet's over them (`album_tag`, `track_tag`), so all the code that reads lofty tags works on them. Sheets in legacy encodings are guessed with chardetng. `load_tracks` reads each sheet and each split file once for all their tracks (`FileCache`). Exported playlists name the tracks the same way, which only Dismas reads. In Flatpak, a `.cue` opened through the document portal from outside the Music folder can't reach its audio file. FLAC's binary CUESHEET block isn't read, only the tag.
- **Playing a part of a file** (`gst_backend.rs`): positions and seeks are relative to the track. A track that doesn't start at 0 only plays once GstPlay says its file is loaded (`TrackLoaded`), as GstPlay drops a seek made before it loads a file; seeks are accurate. When the next track goes on from the end of the current one in the same file, the pipeline plays on, and once the position is past the end the backend sends `TrackAdvanced` (the player confirms it like a hand-over). Otherwise a probe on the audio filter (always set: an identity without ReplayGain) clips the audio at the end and pushes an EOS, so the sink plays the rest and the usual `PlayNext` follows. Only after a track that plays to the end of its file is the next one handed over, and only if it starts at 0. The stream's ReplayGain tags are about the whole file, so a second probe, before rgvolume, sends it the track's gains (from the sheet, or else the file's) as a tag event before the first buffer of each track that reaches the filter, which runs about 2 s ahead of the sink; a tag event only replaces the gains it has. `rgvolume`'s `result-gain` is the gain of the audio passing it, not of what's heard.
- `WaveformGenerator` builds the seek-bar waveform in a separate GStreamer pipeline; for a part of a file, it seeks to it once the pipeline is ready. While `show-waveform` is off, it neither reads the cache nor runs the pipeline. The cached peaks are a small binary format (`encode_peaks`: a versioned header, then two little-endian u16s per quarter second); a JSON file from older versions is converted when it's loaded. At startup, `audio::remove_old_cache_files` removes the cached waveforms and MPRIS covers not used for 90 days; using one touches its mtime.

### UI

- **Composite templates:** each widget is a Rust subclass (`src/*.rs`) bound to a Blueprint template in `src/gtk/*.blp`.
- **Resources:** Meson compiles the `.blp` files to `.ui` and bundles them with CSS and icons through `src/dismas.gresource.xml`. Templates load from `/io/github/dachshund7/Dismas/<name>.ui`.
- **Adding a widget:** update the `.blp` list in `src/gtk/meson.build`, the gresource XML and `po/POTFILES.in` together.
- **Stale resources after editing `.blp` files:** the gresource bundle doesn't track the compiled `.ui` files, so the first `ninja` run can leave the old UI in `_build/src/dismas.gresource`. Run `ninja` a second time.
- **Window coordination:** `Window` is the coordinator. `window.rs` holds its template, properties and `win.*` actions, and its methods are split by area into `window/*.rs`: `bindings.rs` (binding `PlayerState` and the queue to the widgets), `favorites.rs` (the heart button, and marking tracks from their menu), `loading.rs` (opening files, drag-and-drop, restoring the queue), `playlist.rs` (the playlist pane, which shows the queue), `selected_playlist.rs` (selecting, saving, creating, renaming and deleting playlists), `selection.rs`, `albums.rs` (the album grid), `now_playing.rs`, `sidebar.rs`, `sleep_timer.rs` (the sleep timer popover; the countdown itself is `audio/sleep_timer.rs`), `smart_playlists.rs`, `track_menu.rs` and `zen.rs`.
- **The queue's search** (`SearchFilter` in `search.rs`) only filters the pane. Playing a track it found plays it at its place, and Next and the end of a track go through all the tracks, so playback never depends on a search left open in a hidden pane. Its play button (`queue.play-results`) plays the tracks found in place of the queue, with the Undo of `play_in_place_of_queue`. While it filters (`filtering`: the search has words), the rows aren't reorderable, as two rows next to each other can be far apart in the playlist, so tracks dropped on the pane go to the end. Adding tracks (except with `QueueMode::Quiet`) and switching playlists (`replace_selected_playlist`) close it (`close_queue_search`), as the tracks that came in rarely match it, and Show in Playlist, in a result's menu, closes it and flashes the track.
- **The album grid's search** finds albums by their tracks, matched like the queue's (`search_key`). Adding, playing, dragging and opening an album take only the tracks that match (`LibraryView::track_words`, the words `album_files` filters by; the album's tracks get the search's words and filter by them themselves), and the cover of an album matched only partly counts them, as does the banner of its tracks. A Whole Albums toggle then slides in next to the search entry: the grid's `whole-albums` property, which takes all their tracks and hides the counts. It's one setting: the toggle is bound to it in the blueprint, and the album's tracks (`AlbumTracks`'s own `whole-albums`, bound to it by the window) show all their tracks with it and switch it from their banner, which stays in a narrow window, where the pane covers the grid; Go to Album from tracks the search filters turns it on. A new search turns it off once its matches are in (`set_search_matches`), so that a press for the search before doesn't carry over.
- **Fitting the window:** sizes come from measuring the content, since they depend on the font DPI. `PlayerBox` (`player_box.rs`) lays out the player and gives the cover the room left: large, medium or hidden. `TrackCover` draws the size it gets as a square. `Window::size_allocate` measures the split view to set the width where `narrow_breakpoint` collapses it, and the window's size request (`window/sidebar.rs`).
- **Settings:** stored through GSettings (`data/io.github.dachshund7.Dismas.gschema.xml`). The main menu only has actions; the settings are in the Preferences dialog (`preferences_dialog.rs`, Ctrl+,), whose switches are bound to their keys, so what depends on a setting watches it or reads it when needed. Its ReplayGain rows go through `win.replaygain`, the window's `replaygain-mode`, which passes the mode on to the player. `move-from-header-bars`: header bars move the window by default, like other GTK apps (on Wayland it's the only way), and turning it off turns off their drag gestures (`utils::set_window_drag`), right away, for window managers that move windows themselves. Empty areas of the content never move the window. `volume` is saved by the player within half a second of the backend reporting a change, as dragging the slider changes it many times, and at shutdown; it's applied at startup, so the slider is right before anything plays (PulseAudio only restores an app's volume when its stream opens, and keeps one it's given); until it has been saved once, PulseAudio's volume stays. `repeat-mode` is saved whenever the queue's mode changes (from the button, the shortcut or MPRIS) and applied at startup. The window's size is saved by `Window::save_window_state`, when the window is closed and in `Application::shutdown`, as quitting doesn't close it. `playlist-visible` is the user's own choice: the pane button, F9, the back button and Esc go through the window's `user-playlist-visible` (the `queue.toggle` action), which stores it, except in the collapsed split view, where the pane only covers the player for a while. The pane opening or closing by itself (added tracks, drops, search, Show the Playing Track, an empty queue) goes through `playlist-visible` and isn't stored. At startup, restoring the queue doesn't open the pane. `show-waveform` (Show Waveform in Preferences) swaps the `WaveformView` for a stock `Gtk.Scale` (`seek_scale`), bound to the setting's visibility; both seek through `Window::seek_to`. `zen-mode` (Zen Mode): with the playlist pane hidden on the player page, `window/zen.rs` waits 3 s once the pointer leaves the window, focused or not (with focus following the pointer, the window keeps the focus when the pointer goes to an empty part of the screen), then fades out the header bar and the `PlayerBox` children with the `player-controls` class, while `PlayerBox::set_zen_progress` blends the player from its layout with the controls (`shown_layout`) to one without them (`zen_layout`): the cover and the track details move to the middle of the toolbar view, under the faded header bar, and the cover grows into the room that the controls and the header bar leave, as far as the width allows. `TrackCover` draws the square it's given, from the medium size up, so it grows smoothly. Only the allocation changes, not the measured sizes, so the window's size limits stay put. The controls are drawn under the cover and the details as they fade. They fade out over 600 ms (ease-in-out) and back in over 300 ms (CSS's `ease`, quick without jumping), as the cover shrinks back. The pointer entering or the window getting the focus (`is-active`) fades the controls in again, for 3 s if the pointer is elsewhere. Whether the pointer is over the window is asked for (`pointer_widget`) rather than taken from `contains-pointer`: when a drag is let go outside the window, GTK puts the pointer back over the window and no leave follows, so moving over the window brings the controls back too. Each step of a resize starts the wait again, as dragging an edge has the pointer outside the window. On touchscreens, a tap (a touch-only `GestureClick`) brings the controls back and starts the wait again. Faded out, the controls and the header bar don't take input (`can-target`), so a tap can't press a button that can't be seen.
- **Fullscreen** (F11, `win.fullscreen`, a property action on GtkWindow's `fullscreened`): everything follows that property, so the window manager's fullscreen does the same (`window/fullscreen.rs`). It goes to the player and hides the pane without storing it, and leaving goes back to the page and the pane from before; the collapsed split view doesn't show the pane again in fullscreen, and leaving hands the pane to `sidebar_visible_uncollapsed` if the window is collapsed by then, as the window and the breakpoint can change in either order. The `fullscreen` class on the player's `CoverBackdrop` (`cover_backdrop.rs`) makes it larger and always dark, in white over a scrim, and the header bar only has a Leave Fullscreen button. Without a compositor, libadwaita keeps the padding of the window's frame (`window.solid-csd`) in fullscreen, which the stylesheet takes off, as it showed as a light border. The backdrop is the shared cover, blurred small once per cover in another thread (`CoverImage::backdrop`) and scaled up, rather than a blur node, which the renderer could blur again over the whole screen whenever the waveform redraws. Zen Mode's fading applies in fullscreen whatever the setting, once the pointer stays still for 3 s (a motion that doesn't move counts for nothing, as X11 sends some), except while the sleep timer, the more menu or a dialog is open; the pointer hides with the controls. The window's size limits aren't measured in fullscreen, as the larger player would raise the size the window goes back to. Esc leaves fullscreen after leaving selection mode and hiding the pane.
- **Match Cover Art** (`enable-recoloring`): `update_style` (`window/now_playing.rs`) writes the cover's palette as `--background-color-N` on `:root`, and the stylesheet makes tints of them in OKLCH, keeping their hue and a little of their chroma at a lightness set by the color scheme, so the text keeps the theme's contrast. The accent color comes from the most chromatic color, counting less the less of the cover it covers (`cover_image::accent_color`), and is worked out once per cover (`CoverArt::accent`). The share of each color is measured (`CoverImage::shares`), as color-thief orders its palette by pixels times the range of colors, not by coverage. To tune it on real covers, the ignored test `print_palettes` (`audio/cover_cache.rs`) prints the palettes of a music folder. The accent color is behind the `cover-accent` class, since an undefined variable would make the accent color invalid rather than fall back to the system's. High contrast turns it off.
- **The library** keeps a row per track, with the file it comes from (`file`: the track's own, or the `.cue` or image of a sheet); the scan compares the time and size of each file (a `.cue`'s include its audio files'), and reads a changed file's tracks again together. The album grid's covers are thumbnails the scan makes in `~/.cache/dismas/album-covers`, as large as the grid shows them on the monitor with the largest scale (`thumbnail_size` in `library_view.rs`: 240 pixels, or 480 from a scale of 2), and as JPEG, which takes a fraction of the room and of the time to read that PNG does, unless the cover has transparency; their names have the size and the format (`{id}-{size}.jpg`, or `{id}-{size}-alpha.png`), so a thumbnail smaller than that size, or in another format, like the PNG files of older versions, is made again, and `remove_unused_covers` deletes the old one; a larger one is kept (`thumbnail_size`), as the monitors connected can change from one start to the next, and docking a laptop would otherwise make every thumbnail again. GridView keeps hundreds of cells bound around the visible ones (`max-columns` × 30, plus a row before and after), and while the grid scrolls it binds many of them again at about every frame, as its anchor moves back and forth, but it hides the cells off screen (`gtk_widget_set_child_visible`, which unmaps them). So a cell only shows its cover while it's mapped: it's read on bind if the cell is mapped, or when it's mapped, and dropped when it's unmapped (`show_cover`). GTK only shows a cell within 10 pixels of the screen, so each cell coming on screen also reads ahead the covers of the albums a screenful before and after it into the cache (`read_ahead`; a screenful is the number of mapped cells, at most a third of the cache, so that the covers read ahead don't push out the ones on screen), which keeps the 150 most recent ones. Both happen right away, in the map handler: idle callbacks, even at `HIGH_IDLE`, don't run while the grid scrolls, as GTK keeps the main loop busy, so a read-ahead deferred to one ran 13 times in a whole scroll. Opening the grid reads the covers of the ~190 cells GTK maps before it hides the ones off screen, once. Counted on a library of 828 albums, scrolling the grid to its end and back read 14,695 covers before, and about 1,500 since, and 80% of the cells coming on screen found their cover in the cache; the rest waited a frame or two. Tracks without an album tag are grouped by the folder they're in (`album_folder`, where disc folders count as their parent), as an album named after it (`folder_album_title`), which `Track::album` shows too, and searches. Hidden files and folders aren't read (a drive's `.Trash-<uid>` keeps deleted tracks under their names), nor `$RECYCLE.BIN`.
- **Music folders** (`music-folders`, edited in Preferences): an `a(ss)` of URIs, the folder that's read and, for one that came through the document portal, its host path, which names it and tells it apart even once the portal can't (access taken back, or the folder made again, which gives it a new doc ID). An empty list means the XDG Music folder (`library::music_folders`). In Flatpak, the portal gives a folder picked in ~/Music a doc path too, as it grants write access and the manifests only give read access to the Music folder; `resolve_folder` reads it through ~/Music instead, spelled like ~/Music so its tracks keep their paths. Folders are compared by `folder_key` (the host path, or the path without symbolic links), and `roots` leaves out those inside another. Each folder can leave out folders inside it (`MusicFolder::excluded`, paths relative to the folder). They're stored as URIs in a key of their own, `excluded-folders`, because changing the type of `music-folders` would have reset it. In Preferences, a folder's row is an expander that lists them, so they don't make the page longer. A folder picked to leave out is made relative by `relative_to`, which compares `folder_key`s, so picking it through a symbolic link or the portal works. The scan doesn't read them and forgets their tracks, as for a removed folder; until it has run, `LibraryView::reload` hides them along with the unavailable folders. A folder that's missing or empty (often a drive that isn't mounted) is unavailable: its tracks are kept, so they aren't read again when it's back, but hidden, as they can't play (`albums` and `search_albums` take the hidden folders, which `LibraryView::reload` works out), and covers are only made from the tracks that are there, so theirs aren't lost. Removing a folder only changes the album grid: the queue and playlists are lists of files, so they keep its tracks, which the Remove toast says when the selected playlist has some. The library is read again when the Preferences dialog closes, if the folders changed (a scan can't be stopped, so a folder added by mistake isn't read); a scan asked for during another follows it (`rescan_pending`). A hand edit with `gsettings` applies at the next scan.
- **Playlists:** one playlist is selected at a time (the `selected-playlist` setting, empty for the queue). Its tracks are loaded into the player's single `Queue`, which plays them and receives added tracks. Switching stops playback and reloads the `Queue` from the other playlist's file. All playlists are M3U8 files written and read by `playlists.rs`, in the order of their tracks: the queue is `~/.local/share/dismas/queue.m3u8`, and saved playlists are in `~/.local/share/dismas/playlists/`. A name that `check_name` wouldn't allow has no file (`path_in` returns `None`): names also come from the settings and from `win.selected-playlist`, which GtkApplication exports on the session bus, and "../x" would reach other files. Names are at most 243 bytes, as GLib writes to a temporary file named `<name>.m3u8.XXXXXX` first. Shuffling reorders the selected playlist and saves it, keeping the order from before in `~/.local/share/dismas/unshuffled/` (`queue.m3u8`, and `playlists/<name>.m3u8`, so a playlist named "queue" has its own) until the shuffle button is turned off, which puts it back by URI, with the tracks added since at the end. The button shows whether that file exists, for the selected playlist: it's synced from it (`sync_queue_shuffled`) on switching playlists and when the queue empties, and only the button and its shortcut go through the `queue-shuffled` setter, which shuffles or restores. The playing track, or one paused partway, stays first; otherwise the first shuffled track is made current. The file is written before the shuffled playlist, and removed after the restored one is saved, so a crash can't lose the order. It follows renames, goes with deletes, is copied by Save as Playlist, and is dropped when the tracks are replaced (Remove All, the Play buttons, playing dropped files, files opened at startup); the toast's Undo puts the queue's back. They're listed on the Playlists page (`playlists_page.rs`). Importing reads any M3U file, resolving relative paths against its folder and keeping only the tracks found. Exporting writes paths relative to the folder of the file for the tracks under it, so the playlist can be copied with the music to another device. Files dropped on the window go by where they're dropped. A single drop target, on the window's drag overlay (`drag_overlay.rs`), takes them all and works out at each motion what a drop there would do (`file_drop_at` in `window/loading.rs`): on X11 the widgets aren't told the drag left once it's dropped, so a second target that took the drag without getting the drop would keep it and turn the next one down. On the playlist pane, the files go between the tracks where the reordering line shows, or at the end where there's none (on the album's tracks), which the pane's outline shows. Above the first movement of a work, which would be under its header, they go before the work: the line is under the row before it, or above the header of the work at the top. Elsewhere, the overlay shows two zones over the main area: a large one that adds the tracks to the selected playlist, and one below it that plays them in place of the queue, like an album's Play button, with an Undo on the toast that puts back the queue and the playlist that was selected (`undo_replace`). The zones are laid out beside the pane, over the part of the main area that shows: next to the sidebar of the collapsed split view, the content is only drawn moved aside (`PushBin`). There's no modifier key for playing, as the app the files are dragged from reads the keys, and on Wayland Dismas can't see them. Albums are dragged from the grid the same way (`setup_album_drag` in `library_view.rs`), a selected one in selection mode taking the other selected ones, as an `AlbumDrag` that only Dismas takes; they only go to the pane, which is shown while they're dragged if it was hidden, and hidden again if they aren't dropped. Esc cancels the drag, as for tracks, through `utils::cancel_drag`. On X11 without a compositor, the window's input shape is set to its size after each resize (`setup_x11_drop_shape`): GTK's X11 drag sources cache the shapes of the windows, and a window without one never tells them it grew, so drags over the part added by widening the window went to the window below.
- **Smart playlists** (Recently Played, Most Played and Not Heard Lately, on the Playlists page) come from the play stats (`play_stats.rs`), in `~/.local/share/dismas/plays.db`. It's a database of its own because the library's is a cache whose schema bumps drop the tracks, and the history can't be read again from anywhere: its tables are never made again, a later version only changes them in place, and a version newer than the build knows is left alone. The player's `ListenTracker` measures each listen from the positions it's given (whole seconds, four times a second): a step of 1 or 2 s while playing is heard, and anything else (seeks, resume points, going back) only moves the last position. `show_track` ends the listen and starts one for the new track, `clear_current_track` ends it, and so does the end of the queue. Ending keeps the track, so playing it again without `show_track` (`start_over` on a one-track queue, or Stop then Play) is a new listen. A listen is logged from 30 s, or half of a shorter track, and counts as a play (`counted`) from half the track or 4 minutes, whichever is less, as on Last.fm. A track of unknown length needs 30 s and 4 minutes. Listens are written in GLib's pool when they end. On quitting, and before a smart playlist is read, the listen to the track playing is written right away (`save_listen`), so that it's saved, and on the list. Each write adds to the track's all-time `totals` (plays, seconds heard, last played) and drops the listens older than a year. Tracks are told apart by their URI, so a moved file starts again. Recently Played is the last 100 tracks logged, played oldest first, in the order they were last heard, so that a work's movements keep their order; Most Played is the 100 with the most plays in the last 182 days; tracks with the same number of plays are in the order they were last heard, so that a work heard through keeps its movements in order too. Not Heard Lately is like Spotify's Repeat Rewind: the 100 tracks with the most plays all time (from `totals`, so plays older than a year count), at least 3, whose last listen logged, even one that didn't count as a play, is over 61 days old; with as many plays, the ones unheard the longest come first and are kept. Its name avoids "favorite", which means the tracks marked with the heart. Opening one reads the list from the database at that moment, as a snapshot that doesn't change afterwards, and plays it in place of the queue, like dropped files (`play_in_place_of_queue`), with the same Undo, so it's never the selected playlist. Shuffling reads the stats too: each track's all-time plays and when it was last heard (`track_stats`, from `totals`), on the main thread, as the shuffle also saves the playlist there. There's no way yet to clear the history or turn it off. **Favorites** are in `plays.db` too, as they can't be read again from anywhere either: the `favorites` table, added in schema version 2 (the `CREATE TABLE IF NOT EXISTS` of the schema adds it to a version 1 database), keeps each track's URI and when it was marked. The heart button right of the Sleep Timer (`win.favorite`, a property action on the window's `track-favorite`), Ctrl+D and the track menu mark and unmark them; the heart is filled and red, whatever the accent color. `sync_track_favorite` reads whether the playing track is one each time the track changes. They're read and written on the main thread, as each is a single row; if they were written in GLib's pool, like the listens, two clicks close together could be written in the wrong order. Favorites, on the Playlists page, plays them like the smart playlists, in the order they were marked, so that the movements of a work marked one after another keep their order.
- **Pages:** the player, the album grid and the Playlists page take turns in the main area. Each header has the same `PageSwitcher` (`page_switcher.rs`), whose buttons drive the window's `page` property through the `win.page` action. Its playlist pane toggle sits on the left, apart from the page buttons. Its Player button follows `player-available`, which is false while there is nothing to play. Where a header bar is too narrow for the page buttons, the switcher folds them into a menu button during allocation (`set_child_visible`), and measures only the folded width as its minimum; the page titles are in a `FitBin` (`fit_bin.rs`), which hides its child where it doesn't fit. With the album grid's single column, that keeps every page within the 360-pixel minimum, whatever window buttons the desktop shows.
- **Restoring at startup:** a selected saved playlist always reopens. "Restore Queue at Startup" (the `restore-playlist` key, named after Amberol's) only decides whether the queue keeps its tracks; without it, the queue starts empty. Opening Dismas with files replaces the queue. A reopened playlist resumes, paused, from its point in the `resume-points` setting (`resume_point.rs`), and so does a playlist switched back to: by playlist name, the track's URI and its index in the order the tracks were added, and the position. The `Application` saves the selected playlist's point, since it outlives the window, when playback pauses, stops or changes track, when the queue changes, every 30 s while playing, and on quitting (SIGTERM quits too). Switching saves it right away, in `replace_selected_playlist`, as the save at idle would come after the switch. Renaming a playlist moves its point, deleting drops it, and startup drops those of playlists that are gone. Resuming shows the track paused without getting the pipeline ready: `GstBackend::resume_at` keeps the position and seeks when the track plays. A pipeline prerolled to PAUSED that only starts playing a few seconds later stays stuck at its position with PulseAudio.
- **Command line** (`Application::command_line`, with `HANDLES_COMMAND_LINE`): the first Dismas gets the arguments and switches of each `dismas` run, with relative paths resolved in the folder it was run in. Plain files go to `open`, which D-Bus Open from file managers uses too: at startup they replace the queue, and in a running Dismas they're added to the selected playlist, bringing up the window. `--add` adds them to the end of the selected playlist without bringing up a window that's there, hidden or not, and leaves the page and the pane as they are (`QueueMode::Quiet`), so scripts can add tracks while the user does something else. `--play` plays them in place of the queue, like the drop zone (`play_in_place_of_queue`, with its Undo). If Dismas isn't running, both start it by restoring the selected playlist, and then wait until the playlist's tracks are in the queue (`Window::after_startup`): tracks are read in other threads, so tracks read while the playlist loads would land in the middle of it, and the playlist would be saved without its own tracks. Giving both switches is turned down in `handle_local_options`, in the process that was run.
- **Migrating from Amberol:** on the first run (no library, queue or playlists in `~/.local/share/dismas` yet), `migrate.rs` copies them from `~/.local/share/amberol`, through temporary files, and copies the settings changed in the `io.bassi.Amberol` schema if it's installed. The `amberol-migrated` key records that it ran, so clearing the data folder doesn't bring Amberol's settings back. Caches aren't copied; they're made again.

### Translations

- UI strings use gettext helpers from `src/i18n.rs` in Rust, and `_()` / `C_()` in Blueprint.
- `po/*.po` files came from upstream's translators (GNOME's Damned Lies). Don't rewrite them wholesale; when a source string changes, keep the edit to the affected entries. Translations that couldn't follow the rename from Amberol are marked fuzzy. New translatable files go in `po/POTFILES.in`.

## Conventions

- Commit messages: a one-sentence summary line of at most 72 chars, capitalized, with no trailing period. Then a blank line and a prose body explaining *why*. Use `Closes #N` / `Fixes #N` for issues.
- The UI calls audio files "tracks" (not "songs"). Keep the freedesktop icon name `media-playlist-repeat-song-symbolic` as is.
